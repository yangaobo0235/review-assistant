# 报废置换侧边栏字段证据审核工作台改造计划

> 状态：已审核并完成实现（2026-09-12）。
>
> 适用范围：青岛、长春 `scrap_replacement/{region}/1.0`。过户、车源和一致性审核保持现有行为，除非后续单独立项。

## 1. 改造目标

将报废置换审核从“原页面字段旁注入核验标记”改造成“审核助手内完成字段级证据审核、人工取值和受控回填”的工作台。

目标流程：

```text
采集页面字段和材料
  -> 后端 LangGraph 一次完成识别、比对和规则计算
  -> 侧边栏展示页面原值、材料识别值和证据图片
  -> 一致项自动通过
  -> 冲突、缺失或不确定项暂停
  -> 审核员选择保留原值、回填候选值或标记人工复核
  -> 回填成功后继续下一个疑点
  -> 如发生回填，重新采集并执行最终复核
```

核心边界：

- LangGraph 继续一次运行到底，不加入人工 `interrupt`、Checkpoint、恢复 API 或数据库会话。
- 原业务页面保持干净，不再注入“核验成功”“确认无误”“标记异常”等扩展 UI。
- 审核助手展示本次 DOM 实际采集到的可操作控件目录，但默认只处理当前疑点，避免页面字段和页面外核验无限向下堆叠。
- 后端原始结论和前端人工处置分开保存，人工选择不得篡改 `MATCH/CONFLICT/INSUFFICIENT`。
- 所有页面写入都必须由审核员主动触发，并通过页面身份、控件唯一性、回读和失败回滚校验。

## 2. 当前代码基线

当前后端已经具备：

- 固定 10 节点 LangGraph。
- 报废置换页面字段、材料字段和确定性规则。
- `ReviewStep`、`Evidence`、`PageFillAction` 等响应模型。
- 二维码本地识别、官方域名验证和官网字段提取。
- 青岛、长春政策规则，主体关系规则和挂靠填写保护规则。
- 页面采集身份：URL、页面实例、记录指纹、采集 ID。

当前前端仍然存在需要替换的旧方向：

- `page-review-marker.js` 会向原页面添加标记和人工按钮。
- `useScrapReplacementReview` 按“页面标记 + 页面外当前事项”运行。
- `ScrapReplacementReview` 只显示一个页面外人工事项，不显示完整字段证据工作台。
- `page-field-writer.js` 主要只支持两个挂靠字段。
- 任务结束后的最终回填和字段级人工取值尚未形成统一流程。

本计划替代“在原页面逐字段显示核验标记”的方案。已有旧计划文档中的页面标记相关内容不能直接照搬。

## 3. 审核范围和字段语义

### 3.1 页面字段

报废置换当前核心页面字段包括：

- 旧车：回收日期、车架号、车牌号、所有人、发动机型号。
- 新车及发票：发票代码、发票号码、发票金额、开票日期、新车车架号、新车车牌号、新车所有人。
- 页面采集到的其他业务字段按字段矩阵决定是纳入核验、仅展示还是明确标记为无材料核验来源。
- 两个挂靠字段：`old_vehicle.affiliation`、`new_vehicle.affiliation`。

最终字段数量以实际页面采集 fixture 和字段矩阵为准，不允许为了凑数量生成没有证据来源的“自动通过”。

### 3.2 页面外必核验项

侧边栏固定提供以下四组页面外核验：

1. **新车发票产地**：识别值、长春允许范围、政策结果和发票原图。
2. **二维码官网核验**：安全验证后的官网 URL、访问状态、官网 VIN、官网证明编号、图片识别值和一致性。
3. **新旧车主体关系**：主体类型、必要的营业执照企业/法人证据和关系结论。营业执照结构化字段作为该卡片的证据，不单独生成重复卡片。
4. **材料完整性和识别异常**：报废证明、旧车登记证、新车发票的采集、识别、缺失、模糊、失败和超时状态。

### 3.3 合并展示规则

- 新车发票日期的页面值、发票识别值和长春日期政策合并到一个字段详情中。
- 报废交车日期的页面值、报废证明识别值和地区截止日期合并到一个字段详情中。
- 主体关系和营业执照证据合并为一张“新旧车主体关系”卡片。
- 挂靠资格不作为独立页面外卡片，而是并入两个挂靠字段的详情和操作状态。

### 3.4 实施后的字段矩阵

字段目录不能由固定数量或截图清单生成。扩展每次打开页面后扫描实际存在的输入框、下拉框、日期框和可编辑控件，记录标签、值、类型、顺序和规范字段映射；普通只读文本不进入逐字段审核。根据当前长春页面与材料白名单，控件按以下边界处理：

| 处理方式 | 页面字段 |
| --- | --- |
| 页面值与材料值直接比对 | 报废交车日期、报废证明编号、报废车辆车架号、报废车辆车牌号、报废车辆所有人、报废发动机型号、发票代码、发票号码、开票金额、开票日期、新车车架号、新车车牌号、新车所有人 |
| 同时进入字段目录和主体关系核验 | 车辆所有人类型、OCR 新车车架号、客户名称 |
| 无稳定材料来源，不生成虚假核验结论 | 报废车辆类型、新车燃料类型、注册日期、终端证件号、终端客户手机号 |
| 根据主体关系结论核验并联合回填 | 报废车挂靠、新车挂靠 |
| 只读上下文，不进入逐字段审核 | 申请单 ID、申请单编号、申请时间、经销商等普通展示文本 |

当前截图中上述四类可操作控件合计 23 个，但该数字只是当前页面结果，不能写死。页面增删控件后，助手目录和数量必须随 DOM 采集结果变化。未知的新控件也要进入目录并标记“未配置核验规则”，不能静默遗漏；无材料来源的控件显示页面原值并标记“待复核”，不能仅凭页面单一来源标记为通过。

## 4. 材料字段识别和规范化

材料字段名称和页面名称不要求字面一致。识别链路必须保持：

```text
材料图像中的自然语言字段
  -> Qwen 按 DocumentPolicy 提取规范字段
  -> route_fields 按材料类型和页面业务范围路由
  -> normalize_value 标准化
  -> aggregate_field 聚合页面、材料和官网证据
```

当前应保留并测试的语义映射包括：

| 页面概念 | 材料可能名称 | 规范字段 |
| --- | --- | --- |
| 车架号 | 车辆识别代号、VIN、车架号 | `old_vehicle.vin` / `new_vehicle.vin` |
| 车牌号 | 号牌号码、车牌号 | `old_vehicle.plate_no` / `new_vehicle.plate_no` |
| 所有人 | 机动车所有人、车主、购买方名称 | `old_vehicle.owner` / `new_vehicle.owner` |
| 发动机型号 | 发动机型号 | `old_vehicle.engine_model` |
| 报废交车日期 | 交车日期、回收日期 | `old_vehicle.recycle_date` |
| 开票日期 | 开具日期、开票日期 | `invoice.invoice_date` |
| 发票金额 | 价税合计、发票金额 | `invoice.amount` |
| 发票产地 | 产地 | `new_vehicle.origin` |
| 报废证明编号 | 回收证明编号、证明编号 | `scrap_certificate.certificate_no` |

约束：

- 模型只能输出当前材料白名单字段。
- 新旧车归属由页面业务区域决定，不能由模型自行改变。
- 未进入 `DocumentPolicy` 和 `route_fields` 的字段，即使模型看见也不能进入审核结果。
- 新增字段必须同时补充白名单、路由、标准化、证据映射和测试样本。
- 无法可靠区分的字段进入 `uncertain_fields` 或识别限制，不得猜测。

## 5. 后端改造计划

### 5.1 扩展字段审核数据契约

修改：

- `review-agent-service/app/models/review.py`
- `review-agent-service/app/rules/review_step_routing.py`
- `review-agent-service/app/services/review_response.py`

为页面字段审核提供结构化信息：

- 规范字段键、分组、顺序和显示名称。
- 页面原始值及其标准化值。
- 材料/官网候选值，按规范化值聚合。
- 每个候选值对应的材料类型、来源名称、图片 ID、证据框和查看原图能力。
- 字段比较结论。
- 关联政策检查结果。
- 是否允许回填、允许的目标字段和当前页面值状态。

现有 `ReviewStep` 可以保持 API 兼容，但报废置换新增字段级详情模型或扩展字段必须有明确版本策略，不能让前端解析 `reason` 文案猜业务。

### 5.2 重构审核步骤生成

修改 `review_step_routing.py`：

- 所有报废置换页面字段都生成助手内字段项，不再生成 `PAGE_FIELD` 页面注入目标。
- `MATCH` 字段仍生成步骤，用于目录和自动通过统计，但前端默认不暂停。
- 页面缺失、材料缺失、识别不确定、值冲突和政策失败进入待处理队列。
- 日期政策结果合并到对应日期字段的详情数据。
- 外部核验、主体关系和材料完整性生成页面外分组步骤。
- 结果去重仍按稳定 `step_id` 执行，不能按中文标签去重。

### 5.3 二维码官网安全展示数据

二维码结果向前端提供：

- 后端验证后的规范化 HTTPS URL。
- 白名单校验结果。
- 重定向后最终域名校验结果。
- 网页可访问状态。
- 官网返回的 VIN 和证明编号。
- 与图片识别字段的比较结果。

前端只能打开后端验证后的 URL，新标签页打开，不展示或执行未经验证的二维码原始内容。

### 5.4 主体关系和营业执照证据

不新增重复的“营业执照字段”步骤。主体关系结果内部携带：

- 旧车主体类型和名称。
- 新车主体类型和名称。
- 相关营业执照企业名称、法人、统一社会信用代码（必要时展示）。
- 证据图片和证据框。
- 关系判定及缺失/冲突原因。

同一公司名称时可以折叠营业执照详情；不同公司或个人/公司关系时展开所需证据。

### 5.5 最终复核接口边界

本阶段不把人工选择写回 LangGraph 状态，也不引入人工恢复图。发生页面回填后，前端重新采集并创建新的审核任务，使用新的页面值重新执行一次后端审核。

如果后续需要持久化审计，应另行增加审核会话和人工决定 API，不改变本次 LangGraph 一次运行架构。

## 6. 前端工作台改造计划

### 6.1 总体布局

重写报废置换结果界面为三层：

```text
顶部：审核进度、自动通过/待处理/已回填/异常统计
中部：待处理、全部字段、页面外核验三个视图
底部：当前字段的固定操作区
```

不将所有详情纵向展开。默认只显示一个当前疑点；全部字段使用紧凑目录，点击行打开详情。

### 6.2 三个视图

**待处理**：默认入口，只显示冲突、证据不足、政策失败、材料异常、待回填和页面失效项。

**全部字段**：按本次 DOM 采集顺序展示实际可操作控件的紧凑状态列表，并显示实时数量。成功项显示一行摘要，点击后查看完整证据。

**页面外核验**：展示新车发票产地、二维码官网、主体关系和材料完整性四组内容。成功项可折叠，异常项进入待处理。

### 6.3 字段详情

详情至少包含：

- 字段名称和当前处理状态。
- 页面原值。
- 按规范化值聚合后的材料候选值。
- 每个候选值的来源和图片缩略图/原图入口。
- 字段一致性和政策结论分开显示。
- 证据不足或冲突的明确原因。
- 允许的人工动作。

示例：

```text
新车车架号

页面原值：LFNAHULMXT1E06865

材料候选值 A：LFNAHULMXT1E06865
来源：新车发票、机动车登记证

材料候选值 B：LFNAHULMXT1E06835
来源：另一张材料

结论：存在冲突

[保留页面值] [回填选中值] [标记人工复核]
```

### 6.4 状态机

扩展 `reviewSession.ts`，前端状态至少区分：

- `AUTO_PASSED`：后端 `MATCH` 且无需人工处理。
- `PENDING_REVIEW`：需要人工选择。
- `KEPT_PAGE_VALUE`：人工保留页面值。
- `FILLED`：人工选择的候选值已经回填且回读成功。
- `MARKED_EXCEPTION`：人工标记异常。
- `BLOCKED`：页面身份、控件或写入流程失效。
- `COMPLETED`：所有字段和页面外事项已处理。

人工处置记录只存前端内存，并与后端原始状态并列保存。

## 7. 受控回填计划

修改：

- `review-extension/public/page-field-writer.js`
- `review-extension/src/pageFillClient.ts`
- `review-extension/src/hooks/useReviewWorkflow.ts`
- `review-extension/public/content.js`

规则：

- 从“只允许两个挂靠字段”扩展为显式报废置换字段白名单。
- 禁止任意 CSS 选择器、任意字段键和任意宿主按钮操作。
- 回填按钮只在审核员选择候选值后可用。
- 写入前校验页面 URL、页面实例、记录指纹、采集 ID。
- 校验控件唯一、可见、可用、可编辑，必要时确认当前值仍与采集值一致。
- 写入后触发宿主框架需要的事件并回读值。
- 回读失败恢复本次写入前的原值。
- 两个挂靠字段仍然联合预检、成组写入和原子回滚。
- 已有值的字段默认不覆盖，必须明确确认后才允许覆盖。
- 页面刷新、换单、控件重渲染或身份失效时立即阻塞，不重试写入。

## 8. 移除原页面核验 UI

报废置换新流程不再使用：

- 页面成功标记。
- 页面“确认无误 / 标记异常”按钮。
- 页面决定事件订阅。
- 页面标记生命周期作为审核进度来源。

需要评估并清理：

- `public/page-review-marker.js`
- `src/pageReviewClient.ts`
- `content.js` 中的 `SHOW_REVIEW_FIELD_STEP`、决定事件和清理协议。
- 相关 Manifest 加载和测试。

如果原图定位仍然需要 Content Script，只保留安全的 `FOCUS_REVIEW_IMAGE` 能力，不保留页面核验标记能力。

## 9. 最终复核流程

完成字段处理后：

- 未发生回填：展示本轮人工处置摘要，可结束当前助手会话。
- 发生过回填：显示“重新采集并最终复核”。
- 重新采集页面并创建新任务。
- 新任务重新执行字段比较、日期政策、二维码关联和主体关系。
- 保留本轮原始结论、人工动作、写入值和最终复核结果的前端会话摘要。
- 不直接把原始 `CONFLICT` 改写为 `MATCH`。
- 不自动点击宿主业务的提交、通过、驳回或其他决定按钮。

## 10. 分阶段实施

### 阶段 0：字段和来源基线

- 固化实际页面字段 fixture。
- 建立页面字段、材料字段、规范字段、来源、标准化和回填白名单矩阵。
- 为“车辆识别代号/VIN/车架号”等语义变体补充模型桩和路由测试。

### 阶段 1：后端结构化详情

- 扩展字段证据和页面外核验数据契约。
- 重构 `review_step_routing`，保留 LangGraph 节点顺序不变。
- 合并日期政策、主体关系证据和挂靠准入详情。
- 增加后端测试和响应快照测试。

### 阶段 2：侧边栏工作台

- 重写报废置换结果组件。
- 实现进度统计、三视图、紧凑目录、单项详情和证据聚合。
- 实现自动通过和疑点队列。
- 增加窄侧边栏和长文本布局测试。

### 阶段 3：字段级受控回填

- 扩展字段写入协议和白名单。
- 实现候选值选择、确认、回填、回读和回滚。
- 保留页面身份和挂靠原子写入保护。
- 增加文本、日期、下拉控件和失败场景测试。

### 阶段 4：移除原页面标记和最终复核

- 删除报废置换页面核验 UI 及相关事件协议。
- 保留原图定位。
- 实现回填后的重新采集和最终复核。
- 执行旧业务回归。

## 12. 验收标准

- 原业务页面不再注入核验成功、确认无误或标记异常 UI。
- 报废置换每个纳入范围的页面字段都有明确状态、页面原值和材料证据。
- 材料字段名称与页面名称不一致时，能通过规范字段路由和测试覆盖完成比较。
- 新车发票产地、二维码官网、主体关系、材料完整性在助手中可查看且不重复展示。
- 日期政策嵌入日期字段详情，主体关系嵌入营业执照证据。
- 二维码官网地址为后端验证后的安全 URL，审核员可点击新标签页打开。
- 正常项自动通过，疑点项暂停，人工处置后才可继续。
- 审核员可以从字段详情选择候选值回填真实页面，写入有身份守卫、回读和回滚。
- 已有页面值默认不覆盖，挂靠字段仍遵守联合保护和一次性写入约束。
- 回填后可以重新采集并完成最终复核。
- 过户、车源和一致性审核现有行为不回归。
