# 报废置换必传材料与主体证明动态核验改造计划

> 状态：已实施，已完成回归验证（不含提交和推送）。
>
> 适用范围：青岛、长春 `scrap_replacement/{region}/1.0`。过户、车源、一致性审核保持现有行为。

## 1. 目标和已确认决策

本次改造解决两个问题：

1. 将旧车行驶证、旧车登记证、报废机动车回收证明、新车行驶证、新车登记证、新车发票设置为报废置换固定必传材料。
2. 身份证和营业执照不作为所有申请的固定必传材料，而是在“新旧车挂靠关系”核验时根据主体类型动态要求。

已确认的产品边界：

- 六类车辆材料缺失、无法读取或无法确认时，在审核助手“页面外核验”中提示审核员。
- 固定材料不足不终止其余材料识别，但最终结果保持待人工处理，不能自动通过。
- 页面“车辆所有人类型”不再和材料识别类型做普通字段比对。
- 该字段仍作为业务输入使用；在全部字段列表中显示为自动通过，原因固定为“系统业务字段，无需材料比对”。
- 身份证/营业执照不足只在主体关系步骤中提示，不再重复生成一条通用材料不足。
- 原业务页面继续保持干净，不注入材料状态或确认按钮。
- LangGraph 继续一次运行到底；人工确认仍在审核助手前端完成，不引入图中断、Checkpoint 或恢复接口。

## 2. 规则定义

### 2.1 六类固定必传材料

| 业务归属 | 材料 | 最低要求 | 完整条件 |
| --- | --- | --- | --- |
| 旧车 | 机动车行驶证 | 1 份 | 图片可读取且被识别为行驶证 |
| 旧车 | 机动车登记证书 | 1 份 | 必须确认第 1、2 页；允许一张图片同时覆盖两页 |
| 旧车 | 报废机动车回收证明 | 1 份 | 图片可读取且被识别为回收证明 |
| 新车 | 机动车行驶证 | 1 份 | 图片可读取且被识别为行驶证 |
| 新车 | 机动车登记证书 | 1 份 | 必须确认第 1、2 页；允许一张图片同时覆盖两页 |
| 新车 | 机动车销售统一发票 | 1 份 | 图片可读取且被识别为新车发票 |

报废证明二维码仍是独立核验能力，不算第七份材料。报废证明存在但二维码未识别或官网不可访问时，材料本身可记为已上传，二维码核验单独进入待处理。

固定材料状态统一为：

- `PRESENT`：已采集、类型匹配、必需页码可确认。
- `UNCERTAIN`：有图片，但读取失败、类型识别不确定、必需页码无法确认或关键区域模糊。
- `MISSING`：页面对应材料位置没有图片，或提取后没有任何对应材料。

`UNCERTAIN` 允许审核员打开原图后人工确认；`MISSING` 默认要求补传。若以后允许缺件放行，必须单独增加有审计记录的例外操作，本次不把“确认已核对”当成材料真实存在。

### 2.2 车辆所有人类型字段

页面字段 `application.owner_type` 按以下方式处理：

- 采集其原始值，只接受页面明确选项“个人”或“企业”。
- 不再生成“页面值 vs 材料推断值”的 `AFFILIATION-AUX-OWNER-TYPE` 比对。
- 若该控件出现在本次 DOM 字段目录中，生成自动通过步骤，原因是“系统业务字段，无需材料比对”。
- 该自动通过只表示“不需要审核这个字段”，不表示身份证、营业执照或主体关系已经通过。
- 页面值为空、超出“个人/企业”范围或同一控件采集到多个值时，不能默认通过，转入人工确认主体类型。

安全边界：如果车辆材料中的所有人名称明显与页面类型无法对应，例如页面为“个人”但材料主体为“某某有限公司”，不回头把该页面字段判为冲突；在“新旧车挂靠关系”中显示“主体类型与材料主体无法可靠对应”，暂停人工处理。

### 2.3 主体证明动态要求

挂靠关系规则分别建立旧车主体和新车主体，不把一个“车辆所有人类型”值无条件套到双方：

- 新车/申请主体：优先采用页面 `application.owner_type`，同时读取新车行驶证、登记证和发票中的所有人/购买方名称。
- 旧车主体：读取旧车行驶证、登记证和报废证明中的所有人名称，再根据明确名称形态及已上传主体证件确定类型。
- 名称只能作为辅助分类。无法可靠判断时，不同时误报身份证和营业执照缺失，而是要求审核员先选择主体类型。

主体证明要求：

| 主体类型 | 动态要求 |
| --- | --- |
| 自然人（页面“个人”） | 身份证正面和反面 |
| 企业或其他组织（页面“企业”） | 与主体名称对应的营业执照 |
| 名称显示为个体工商户/经营部且上传营业执照 | 营业执照；如需要用经营者身份建立关系，再要求经营者身份证正反面 |
| 无法可靠判断 | 暂停，由审核员确认主体类型后再判断缺件 |

这里将口语中的“个体个人”和法律意义上的“个体工商户”区分：普通自然人只要求身份证；真正的个体工商户有营业执照，涉及经营者关系时还需要经营者身份证。

### 2.4 新旧车主体组合

| 组合 | 最低主体证据 | 关系结论 |
| --- | --- | --- |
| 同一自然人 | 一套身份证正反面，身份证姓名与双方所有人一致 | 证件齐全且姓名一致后通过 |
| 两个不同自然人 | 每个不同主体各自的身份证正反面 | 默认进入人工复核，不自动认定挂靠关系 |
| 同一企业 | 一份与企业名称对应的营业执照 | 法定名称一致且证件明确后通过 |
| 两家不同企业 | 两家企业各自的营业执照 | 比较双方营业执照法定代表人/负责人 |
| 一方自然人、一方企业 | 自然人身份证正反面 + 企业营业执照 | 比较身份证姓名与企业法定代表人/负责人 |
| 一方为个体工商户 | 个体工商户营业执照；必要时加经营者身份证 | 比较经营者与另一方主体 |

一份主体证件只能满足与其名称匹配的主体要求。两家公司名称不同而只上传其中一家营业执照时，必须明确指出缺少哪一方的营业执照。

### 2.5 身份证隐私和可用性

- 身份证只提取挂靠关系必需的信息：姓名、正反面类型；身份证号码如技术上必须使用，只在传输和展示时脱敏。
- 日志、错误信息、测试快照和审核助手不得输出完整身份证号码。
- 身份证反面不单独承担人员姓名判断，只用于确认材料正反面齐全。
- 当前页面如果只支持一套身份证正反面，而规则需要两套身份证，结果必须说明页面材料槽位能力不足并转人工，不能假装证据齐全。

## 3. LangGraph 执行位置

不新增节点，沿用当前 10 节点顺序：

```text
validate_context
  -> assess_collected_materials       固定六类材料的采集阶段检查
  -> extract_documents                增加身份证识别，继续识别营业执照和车辆材料
  -> assess_extracted_evidence        固定六类材料的类型/页码完整性检查
  -> run_external_checks              报废证明二维码官网核验
  -> compare_same_fields              跳过车辆所有人类型的材料比对
  -> run_business_rules               动态计算主体证明要求并核验挂靠关系
  -> prepare_review_steps             生成两组页面外材料卡片和字段目录
  -> derive_recommendation
  -> build_final_response
```

动态主体材料依赖材料提取后的所有人、营业执照和身份证结果，因此放在 `run_business_rules`，不塞进固定材料完整性策略，也不提前在 `assess_collected_materials` 误报。

## 4. 后端改造

### 4.1 固定材料策略

### 4.2 身份证文档能力

实施内容：

- 营业执照继续提取企业名称、法定代表人/负责人、统一社会信用代码。

### 4.3 主体证据规则模型

在 `affiliation_subject_checks.py` 中增加结构化主体证据要求，不让前端解析中文原因猜状态。建议新增：

- `party`：`OLD_VEHICLE`、`NEW_VEHICLE` 或 `SHARED`。
- `subject_name`、`subject_type`。
- `required_documents`：身份证正面、身份证反面或营业执照。
- `matched_image_ids`。
- `status`：`PRESENT`、`MISSING`、`UNCERTAIN`。
- `reason`。

规则执行步骤：

1. 分别聚合旧车、新车所有人名称，名称冲突先返回证据不足。
2. 读取页面新车/申请主体类型；为空或非法值时暂停。
3. 判断旧车主体类型；不确定时暂停，不猜测必传证件。
4. 按主体组合生成最小主体证据集合，并按规范化名称匹配证件。
5. 检查身份证正反面、营业执照关键字段及多份冲突。
6. 证据齐全后再计算同一主体、同一法人或个人与法人的关系。
7. 只有关系为 `MATCH` 时才生成两个挂靠字段的联合回填动作。

### 4.4 跳过所有人类型字段比对

修改 `affiliation_subject_checks.py`、`review_step_routing.py` 和字段配置：

- 移除 `AFFILIATION-AUX-OWNER-TYPE` 作为实际比对项。
- 保留页面值给主体规则使用。
- DOM 中该控件生成稳定的字段步骤并自动通过，不携带伪造材料证据。
- 不允许审核员从 OCR 候选值回填该系统字段。

### 4.5 最终建议和去重

- 六类固定材料的 `MISSING/UNCERTAIN` 作为强制待处理项进入最终建议。
- 主体证件不足只由“新旧车挂靠关系”输出一次，不再次追加到固定材料清单。
- 页面类型与材料主体无法对应、证件名称不匹配、多份证件冲突都必须进入人工复核。
- 材料缺失、字段冲突、二维码异常保持独立原因，不能合并成一条模糊提示。

## 6. 审核助手页面外核验

修改 `ScrapReplacementReview.tsx`、类型定义和展示适配器。

页面外核验保留紧凑列表，不把每种材料展开成独立长卡片：

### 6.1 车辆材料完整性

一张卡片固定展示六行：

```text
旧车行驶证                 已确认
旧车登记证第 1、2 页       已确认
报废机动车回收证明         已确认
新车行驶证                 缺失
新车登记证第 1、2 页       第 1 页无法确认
新车发票                   已确认
```

- 成功项默认折叠为一行。
- 缺失和不确定项排在前面并进入“待处理”。
- 有图片的行提供“查看原图”；真正缺失的行不展示无效查看按钮。
- 不在原业务页面显示任何成功或异常标记。

### 6.2 新旧车挂靠关系

一张卡片展示：

- 旧车主体名称、主体类型及判断来源。
- 新车主体名称、页面声明类型及材料名称。
- 每一方当前要求的身份证/营业执照及状态。
- 已识别的企业名称、法人/负责人、脱敏身份信息和证据图。
- 最终关系结论与具体缺件原因。
- 关系通过后才显示“填写挂靠字段”。

“车辆所有人类型”在全部字段中自动通过，但不在页面外核验再生成一张重复卡片。

## 9. 验收标准

- 六类固定材料任一缺失时，审核助手页面外核验准确指出缺少哪一份，最终不能自动通过。
- 六类全部存在时显示六行已确认，不再只显示三类材料。
- 页面“车辆所有人类型”不再因材料推断产生字段冲突，且无需人工操作。
- 页面为个人时才要求身份证正反面；页面为企业时才要求营业执照。
- 新旧车主体分别计算，不能用一个主体类型覆盖双方。
- 证件存在但名称不对应时仍然证据不足，不能只按图片数量通过。
- 身份证/营业执照不足只在挂靠关系中出现一次。
- 挂靠关系通过前不得回填挂靠字段。
- 审核员能从材料或主体关系卡片直接查看对应原图。
- 不在原业务页面注入核验 UI，不引入 LangGraph 人工中断，不影响其他业务 Profile。

## 10. 审核时需要重点确认的一个边界

当前样例页面“车辆所有人类型”为“个人”，而前面新车发票和登记证中的购买方/所有人看起来是企业名称。如果这些截图属于同一申请，说明该页面字段可能不是“新车实际所有人类型”，或者它虽然由后端提供但业务含义与材料主体不同。

实施时将采用以下保护：页面字段仍不做普通字段核验，但一旦它驱动出的身份证/营业执照要求与新车材料主体明显无法对应，挂靠关系必须暂停并提示审核员确认，不能因为字段由后端写入就直接放行。审核通过本计划时，应同时确认该字段究竟表示“申请人类型”还是“新车所有人类型”；这会决定它能否作为新车主体证明要求的首要依据。
