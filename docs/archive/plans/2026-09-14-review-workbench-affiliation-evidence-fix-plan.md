# 车辆审核工作台问题修复计划

- 日期：2026-09-14
- 范围：\`review-agent-service\` 后端审核数据与 \`review-extension\` 浏览器插件工作台
- 当前阶段：仅计划，待用户审查通过后实施

## 1. 目标与验收结果

1. “待处理”“全部字段”“页面外核验”标签均显示真实数量，并随数据刷新同步。
2. 每个审核字段先显示页面原始值，再显示材料提取值；每条材料值都有对应缩略图和“查看原图”入口。
3. 页面原始值只来自真实表单控件或可确认的字段节点，不包含“不一致”“易混淆”等装饰文本。
4. VIN、手机号等值进行字符级比较，差异字符在识别文本中标红；空值、长度不一致、大小写规则有明确处理。
5. \`old_vehicle.affiliation\` 显示为“报废车挂靠”，\`new_vehicle.affiliation\` 显示为“新车挂靠”，布局稳定。
6. 主体关系规则通过且目标字段可定位时，自动在真实页面下拉框选择“公司”（兼容“企业”等同义选项），写入后回读确认。
7. 二维码核验结果及其下方内容不再错位或被全局 \`dl/dt/dd\` 样式挤压。
8. “新车发票产地”按统一证据卡片展示提取值、图片和原图入口。
9. “材料完整性与识别异常”列出具体核验材料、状态、异常原因及关联图片。
10. 新旧车挂靠关系按既有业务规则判断；辅助 OCR 检查不无故覆盖或阻断已通过的主体关系结论。

## 2. 根因与处理原则

### 2.1 页面原始值污染

采集器当前可能从外层容器或标签文本拼接值，混入状态徽标和提示语。改为“控件优先、语义节点兜底”的采集策略：

- \`input/textarea/select\` 读取 \`value\`、选中项和可访问标签；
- 非控件节点仅在有稳定字段标识时读取；
- 去除装饰节点（badge、tooltip、status、diff 等）而不是写死删除某几个词；
- 为每个采集值保留来源节点类型、字段 ID、页面指纹，便于诊断。

### 2.2 挂靠下拉未真正写入

写入器需要把“生成意图”与“页面操作”分层验证：

1. 根据字段 ID、标准化标签和页面指纹定位活动表单；
2. 识别原生 \`select\`、Ant Design、Element 等 combobox；
3. 打开下拉并在 Portal/虚拟列表中按规范化文本匹配“公司/企业”；
4. 触发框架兼容的 input/change/blur 事件；
5. 回读控件值或选中标签，确认确实选中；
6. 失败时记录阶段化原因（定位、打开、匹配、事件、回读），不静默成功。

只有主体关系规则满足预设条件才执行写入；不以无关 OCR 辅助项替代业务规则。

### 2.3 证据区排版

证据卡片使用独立 class 和 CSS grid/flex，不继承全局 \`dl\` 的两列规则。每项材料固定为：

\`材料提取值（字段名 + 值） | 缩略图 | 查看原图\`

在窄屏下允许整行换行，长 VIN、统一社会信用代码和公司名使用正常断行。

## 3. 具体改动分层

### A. 后端数据契约与审核流程

涉及：

- \`review-agent-service/app/agent/workflow.py\`
- \`review-agent-service/app/services/review.py\`
- \`review-agent-service/app/businesses/profiles.py\`
- \`review-agent-service/app/rules/review_step_routing.py\`
- \`review-agent-service/app/rules/affiliation_subject_checks.py\`
- 新车发票产地相关 policy/rule 文件
- 对应 schema/model 与测试 fixture

计划：

1. 统一字段展示元数据：内部字段 ID、中文标签、控件类型、是否可回填。
2. 输出页面值、材料值、来源图片、差异片段、核验状态的稳定结构。
3. 让 affiliation 的中文标签由字段元数据统一提供，避免组件自行猜测。
4. 保持主体关系既有判定规则；明确辅助检查是提示还是阻断，并在代码中显式表达。
5. 将材料完整性报告中的 checklist/issues/image_ids 完整传给前端。
6. 确保“新车发票产地”使用统一 evidence 结构，而不是特殊分支。

### B. 页面采集、写入与消息链路

涉及：

- \`review-extension/public/page-field-collector.js\`
- \`review-extension/public/page-field-writer.js\`
- \`review-extension/public/content.js\`
- \`review-extension/src/hooks/useReviewWorkflow.ts\`
- \`review-extension/src/hooks/useScrapReplacementReview.ts\`

计划：

1. 重构采集器的字段定位和文本清洗为通用规则，禁止针对 VIN/手机号写死替换。
2. 扩展字段快照：原始 DOM 来源、控件类型、标准化值、页面指纹。
3. 自动下拉执行增加可观测日志和失败原因，并确保幂等、回读、失败回滚。
4. 页面身份变化或控件失效时重新采集后再尝试一次，避免旧 snapshot 导致写入失败。
5. 将后端 \`page_fill_intent\` 映射到真实字段，不通过显示文案反推字段。

### C. 前端展示与交互

涉及：

- \`review-extension/src/components/ScrapReplacementReview.tsx\`
- 相关字段/证据组件
- \`review-extension/src/valueDiff.ts\`
- \`review-extension/src/App.css\`

计划：

1. 顶部标签统一由同一份列表派生数量。
2. 重做字段证据卡片：页面原始值区、材料提取行、缩略图、查看原图、回填按钮。
3. 删除“图片识别”等冗余来源文案和重复的“申请页面字段”材料行。
4. 回填与查看原图采用明显不同的颜色、hover 和禁用状态。
5. 使用字符级 diff 渲染，保留相同字符，差异字符标红；处理长度不一致和空值。
6. 专门修复二维码区域、长文本和下拉结果的布局。
7. 材料完整性区展示每一项材料的“已核验/缺失/异常”、异常说明和图片证据。
8. 挂靠字段使用中文标签并以正常表单行布局展示规则结论与写入状态。

## 4. 测试与验证

- 后端：workflow、主体关系、发票产地、材料完整性、review step routing。
- 前端：字段标签映射、数量派生、字符级 diff、证据卡片数据转换。
- 页面脚本 fixture：原生 select、Ant Design/Element combobox、Portal 选项、虚拟列表、React/Vue 事件和失败回读。
- 构建：\`npm run build\`；测试：现有测试及新增关键场景测试；后端运行相关 pytest。
- 使用真实页面 snapshot 核对 VIN/手机号原始值、两个挂靠字段实际选中“公司”、二维码/发票产地证据、材料清单与页面外核验数量。

## 5. 实施顺序

1. 确认后端数据契约和字段元数据。
2. 重构页面采集与下拉写入，并用 fixture 验证真实 DOM 操作。
3. 替换前端证据卡片、diff 和布局。
4. 联调数量、材料完整性、二维码和发票产地并运行相关测试。
5. 每阶段提交可独立审查的 diff，不覆盖工作区已有无关修改。

## 6. 风险与所需信息

- 当前无法直接读取用户 Chrome 实时 DOM（连接提示 \`Codex auth token is unavailable\`）。若 fixture 与真实结构仍有差异，需要一次插件诊断日志或脱敏 DOM 片段。
- 工作区已有未提交修改，实施前会先检查并严格限制改动文件。
- 若现有响应缺少原图 URL，需要先确认图片服务的稳定访问方式。

## 7. 用户审查点

请审查证据卡片横向布局、公司/企业匹配范围、字符差异标红规则、材料清单名称，以及主体关系通过后的自动回填条件。用户确认计划后，才开始修改业务代码。
