# 报废置换动态证据来源与字段级人工复核改造计划

> 状态：已获准实施，进行中。
>
> 适用范围：青岛、长春 `scrap_replacement/{region}/1.0`。
> 过户、车源、一致性审核保持现有行为。

## 1. 改造背景

当前审核助手已经能够采集页面字段、识别材料并展示核验结果，但仍存在以下问题：

1. 字段来源按固定“主要来源/辅助来源”理解，容易把某份材料没有字段误判为异常。
2. 某个字段只在一份材料中出现时，可能被判为 `INSUFFICIENT`，增加不必要的人工复核。
3. 同一字段的页面值、图片识别值和 OCR 提示混在一起，导致 VIN 等字段出现错误冲突。
4. 证据来源没有在字段对应位置逐一展示，审核员无法快速知道某个值来自哪张图。
5. 审核员只能在真实页面中修改字段，识别结果错误时操作成本高。
6. 每个字段没有独立的“确认无误/标记异常”状态，也不能将所有异常项整理回填为页面驳回原因。
7. 二维码、主体关系和结构化证据存在长文本换行、内容混杂、页面过长等展示问题。

本计划的目标是把审核助手改造成“按字段核验、按证据展示、人工确认后回填”的工作台，同时保持原业务页面干净，不在原页面增加核验标记。

## 2. 已确认的产品原则

### 2.1 不设置强制存在的固定主要来源

“主要来源”不再表示所有申请都必须上传且必须识别出该字段的材料。

每个字段配置以下信息：

- `allowed_sources`：允许参与该字段核验的材料类型集合。
- `preferred_sources`：在多个有效证据同时存在时的参考顺序，只是优先级，不是必传条件。
- `evidence_mode`：单一来源、可用证据、并列证据或规则推导。
- `missing_behavior`：字段未出现时的处理方式。

运行时只使用实际识别到的有效证据：

```text
识别到 0 份有效证据：显示“未发现字段”，不自动判定冲突。
识别到 1 份有效证据：按单一有效证据继续核验，不因证据数量少而待复核。
识别到 2 份及以上：比较归一化后的值，只有值不一致才进入人工复核。
```

材料中没有某个字段，不等同于材料缺失；材料缺失只由材料完整性规则判断。

### 2.2 “主要来源”只在运行时动态产生

当字段有多个有效来源时，系统可以依据 `preferred_sources` 选择一个“当前参考证据”，但该来源必须实际存在。

例如发动机型号：

```text
允许来源：登记证书、行驶证、回收证明
优先顺序：登记证书 > 行驶证 > 回收证明
```

如果登记证书没有发动机型号、行驶证有，则行驶证成为当前参考证据，不得因为登记证书缺少字段而挂起审核。

### 2.3 缺失、单一证据和冲突必须区分

- `NOT_FOUND`：允许来源中没有识别到字段，仅提示信息。
- `SINGLE_EVIDENCE`：识别到一份有效证据，可以继续审核。
- `MATCH`：多个有效证据归一化后相同，或单一来源核验通过。
- `CONFLICT`：多个有效证据或页面值与证据之间存在真实差异。
- `REVIEW_REQUIRED`：存在 OCR 不确定、语义无法归一化、页面值为空但业务要求确认等情况。

`NOT_FOUND` 和 `SINGLE_EVIDENCE` 默认不进入待处理列表，除非该字段另有明确的业务必填规则。

### 2.4 大模型只负责识别，不负责决定业务来源优先级

模型负责识别：

- 材料类型；
- 图片中出现的字段及字段值；
- OCR 置信度和易混淆提示；
- 结构化字段。

确定性规则负责决定：

- 哪些材料允许参与该字段；
- 是否需要比较多个来源；
- 哪个来源只是优先参考；
- 缺失是否影响审核；
- 是否生成待人工处理项。

### 3.3 来源模式定义

- `SYSTEM`：系统或页面业务字段，不与图片 OCR 比对。
- `SINGLE_SOURCE`：业务上只认指定材料；材料未出现字段时只提示，不伪造其他来源。
- `AVAILABLE_EVIDENCE`：从允许来源中动态选择实际存在的有效证据；优先顺序不构成硬性要求。
- `PARALLEL`：所有实际出现的来源平行展示和比较，不设置主要来源。
- `PAGE_AUXILIARY`：页面辅助字段，与对应业务字段关联展示，不作为独立材料来源重复制造冲突。
- `DERIVED`：由确定性规则根据多个字段或主体证据推导，不直接把某张图片作为最终结论。

## 4. 证据模型改造

### 4.1 每条识别结果必须保留来源定位

每条证据至少包含：

- `field`：规范字段名；
- `value`：清洗前识别值；
- `normalized_value`：用于比较的归一化值；
- `source_type`：材料类型或页面字段；
- `image_id`、`image_index`；
- `group_title`、`group_order`；
- `confidence`；
- `uncertain`；
- `detail`：易混淆字符等提示。

前端不得通过拼接 `source` 字符串推断材料类型，必须使用结构化字段展示“第几张图片、哪类材料”。

### 4.2 归一化规则

不同字段使用不同归一化器，不能使用一个通用字符串清洗规则：

- VIN：大写、去除空格和换行，保留字符位置；“易混淆”作为独立警告，不拼入值。
- 车牌号：去除空格和分隔符，统一大小写；保留省份简称和新能源牌照结构。
- 企业名称：去除无意义空格和标点，但不随意删除“有限公司”“分公司”等主体后缀。
- 日期：统一为 `YYYY-MM-DD`。
- 金额：去除货币符号和千分位后按数值比较。
- 车辆类型：建立同义词和层级归一化，区分车型、用途和燃料类型，不能把“中型仓栅式货车”简单截断成“货车”。
- 身份证和统一社会信用代码：只做格式清洗和脱敏展示，不在日志中输出完整敏感值。

### 4.3 缺失字段的处理

后端必须区分以下情况：

```text
材料没有该字段：NOT_FOUND
材料存在但 OCR 失败：UNCERTAIN
材料识别到一个值：SINGLE_EVIDENCE
材料识别到多个相同值：MATCH
材料识别到多个不同值：CONFLICT
```

不能因为某个允许来源没有字段，就减少其他有效证据的可信度，也不能把 `NOT_FOUND` 转换成通用的“材料不足”。

## 5. 字段级审核助手设计

### 5.1 字段卡片统一结构

每个字段使用一张紧凑卡片：

```text
字段名称                         一致 / 冲突 / 待确认

页面原值：...

证据来源
  图片 1 · 旧车行驶证：...
  图片 2 · 旧车登记证：...
  图片 3 · 回收证明：未发现该字段

自动结论：已发现 2 份有效证据，证据一致
识别提示：无 / 存在易混淆字符 / 语义待确认

人工确认值：[________________]

[确认无误] [标记异常] [回填到页面]
```

要求：

- 每个证据值显示对应图片编号和“查看原图”入口；
- 没有该字段的图片显示“未发现该字段”，不显示无效图片按钮；
- 单一有效证据默认不进入待处理列表；
- 自动通过项默认折叠，待处理项置顶；
- 页面原值、识别值、人工确认值三者分开显示；
- 长企业名称、统一社会信用代码和二维码 URL 必须正常换行或折叠，不能逐字符竖排。

### 5.2 人工复核操作

每个字段提供两个必需操作：

- `确认无误`：将本地审核状态改为 `CONFIRMED`，展示状态改为“一致”。
- `标记异常`：将本地审核状态改为 `REJECTED`，要求记录审核员可编辑的问题说明。

`确认无误` 不修改后端自动判断，只修改当前审核会话的人工处置状态。

`标记异常` 的记录至少包含：

- 字段名称；
- 页面原值；
- 识别证据值及来源图片；
- 自动冲突原因；
- 审核员补充说明。

### 5.3 人工值回填

- 审核员可以在助手字段卡中编辑人工确认值；
- 只有字段存在有效页面写入目标时才显示“回填到页面”；
- 回填前显示页面当前值，页面已经有值时要求确认覆盖；
- 回填后必须重新读取页面并更新页面指纹；
- 只读字段允许人工确认，但不提供回填按钮；
- 除现有 `old_vehicle.affiliation` 和 `new_vehicle.affiliation` 外，是否允许写入其他页面字段必须通过独立白名单配置，不得根据字段名自动放开；
- 页面失效、控件消失、字段值发生变化时，停止回填并提示重新采集。

## 6. 驳回原因回填

### 6.1 本地问题记录

前端维护当前审核会话的问题列表：

```ts
interface ReviewerIssue {
  field: string;
  label: string;
  pageValue: string;
  evidenceValues: Array<{
    value: string;
    source: string;
    imageId?: string;
  }>;
  reason: string;
  note: string;
}
```

问题列表只记录审核员点击“标记异常”的字段，不把自动识别的所有待确认项直接写入驳回原因。

### 6.2 回填方式

在真实页面点击“驳回”之前，审核助手提供“整理驳回原因”动作：

```text
1. 新车车架号：页面值 LFNAHULX5T1E07836，
   图片 2（新车登记证）识别为 LFNAHULX5T1F07836，存在字符差异。
2. 报废车辆所有人：页面值与图片 1（旧车行驶证）识别结果不一致。
```

回填动作只允许定位和填写“驳回原因”文本框，不自动点击“驳回”或“立即提交”。

必须校验页面 URL、页面实例、页面指纹和采集 ID，防止把上一条申请的问题写入当前申请。

## 7. 页面外核验改造

### 7.1 二维码官网核验

改为独立、紧凑的二维码核验卡片：

- 显示二维码识别状态；
- 显示识别出的官网 URL，最多两行，超长部分可展开；
- 只有通过域名校验且可访问时显示“打开官网”链接；
- 官网返回字段按“字段名、官网值、页面值、结论”展示；
- URL 不得撑开卡片或导致逐字符换行；
- 官网不可访问、域名不合法、官网值与页面值冲突分别展示原因。

### 7.2 新旧车挂靠主体关系

主体关系不再把营业执照、客户名称、OCR VIN 和主体类型平铺混在一起，而是分为三层：

```text
主体概览
  旧车主体名称、主体类型、来源
  新车主体名称、主体类型、来源

主体证据
  旧车所需身份证/营业执照及状态
  新车所需身份证/营业执照及状态
  对应图片和结构化识别字段

关系结论
  新旧车主体是否一致
  个人/企业关系是否满足规则
  旧车挂靠建议
  新车挂靠建议
```

只有主体关系和所有保护条件都通过时，才显示挂靠字段回填动作。

### 7.3 材料完整性

保持六类固定材料清单，但字段级“未发现字段”不再进入材料完整性异常：

- 材料完整性只判断材料是否上传、类型是否正确、必需页是否存在、图片是否可读取；
- 字段未出现在某张材料中由字段证据卡说明；
- 六类材料的缺失仍然是材料层面的待处理事项；
- 材料卡不重复列出每个字段的识别缺失。

## 8. LangGraph 设计

LangGraph 继续一次运行到底，不将审核员每个字段的点击动作加入图中，不新增人工中断、Checkpoint 或恢复接口。

节点职责保持如下：

```text
validate_context
  -> assess_collected_materials
  -> extract_documents
  -> assess_extracted_evidence
  -> run_external_checks
  -> compare_same_fields
  -> run_business_rules
  -> prepare_review_steps
  -> derive_recommendation
  -> build_final_response
```

改造点：

- `extract_documents` 返回每条字段证据的材料和图片定位；
- `assess_extracted_evidence` 只做材料类型、页码和读取质量判断；
- `compare_same_fields` 使用字段来源策略和归一化器，不把缺失字段当冲突；
- `run_business_rules` 计算主体关系和挂靠建议；
- `prepare_review_steps` 为每个页面字段生成证据来源和人工操作元数据；
- `derive_recommendation` 区分自动结论和人工会话状态，不能把单一证据自动抬高为待复核。

人工点击、人工输入和页面回填全部属于扩展前端会话层，由前端维护，不改变 LangGraph 已返回的审核事实。

## 9. 后端改造任务

### 9.1 新增字段来源策略注册表

建议新增独立模块，例如：

```text
review-agent-service/app/rules/field_evidence_policies.py
```

注册表必须包含：

- 页面字段；
- 来源模式；
- 允许材料类型；
- 优先参考顺序；
- 是否允许单一证据通过；
- 未发现字段的结果状态；
- 归一化器名称；
- 页面回填能力。

不能从中文 label、图片顺序或模型返回的 source 文本临时猜来源策略。

### 9.2 重构字段比较

修改字段比较和证据聚合逻辑：

- 先按规范字段聚合证据；
- 再按允许来源过滤；
- 只对实际存在的证据比较；
- 采用字段专用归一化器；
- 保留原始值和归一化值；
- 将 OCR 易混淆提示放入 `detail`/`uncertain`；
- 页面 OCR 新车车架号与新车车架号建立关联，不作为无来源的冲突值重复计算。

### 9.3 调整审核步骤状态

后端 `ReviewStep` 或等价模型增加：

## 11. 测试计划

### 11.1 后端单元测试

- 固定主要来源不存在但辅助来源存在时，不产生材料不足异常。
- 只识别到一份允许证据时，状态为单一有效证据，不要求人工复核。
- 识别到零份证据时为 `NOT_FOUND`，不自动升级为冲突。
- 并列字段识别到两份相同值时通过。
- 并列字段识别到两份不同值时冲突。
- 页面值与唯一证据一致时通过。
- 页面值与唯一证据不一致时进入人工复核。
- VIN“易混淆”提示不拼接到比较值中。
- VIN、车牌、日期、金额、企业名称和车辆类型使用各自归一化规则。
- 发票代码不会从发票号码自动复制。
- OCR 新车车架号不作为重复独立材料源制造冲突。
- 车辆所有人类型始终使用系统字段规则，不与 OCR 主体类型普通比较。
- 主体关系分别计算旧车和新车主体，不以一个主体类型覆盖双方。

### 11.2 前端单元和接线测试

- 字段卡展示每个证据的图片编号和材料名称。
- 同一字段缺少某份材料时显示“未发现字段”，不显示“材料不足”。
- 单一证据字段不进入待处理计数。
- 冲突字段展示页面原值、各来源值和原图入口。
- 点击“确认无误”后状态变为“一致”。
- 点击“标记异常”后生成结构化问题记录。
- 人工输入值可以覆盖识别建议值，但不会立即修改真实页面。
- 只有点击回填后才调用页面写入客户端。
- 只读日期字段没有回填按钮。
- 二维码长 URL 可以展开，不能撑坏布局。
- 主体关系卡片不混入无关 OCR 字段。
- 驳回原因只包含审核员明确标记不通过的字段。
- 驳回原因回填不触发“驳回”或“立即提交”。

### 11.3 真实页面验收

至少验证以下场景：

1. 三份旧车材料、新车三份材料字段齐全且一致。
2. 某字段只出现在一张材料中，审核继续，不进入待处理。
3. 某字段在一张材料中缺失，但其他材料有值，不判材料不足。
4. 某字段两张材料识别值冲突，进入该字段人工复核。
5. 页面值与唯一图片证据冲突，能够人工修改、确认并回填。
6. VIN 带“易混淆”提示但实际值一致，不错误判为冲突。
7. 发票只有发票号码，没有发票代码时，不复制号码到代码字段。
8. 电子发票“一键验真”仍由真实页面既有逻辑执行，助手不模拟或重复提交。
9. 个人主体只要求身份证正反面，企业主体只要求对应营业执照。
10. 新旧车主体关系通过后，挂靠字段才显示受控回填动作。
11. 存在多个不通过字段时，驳回原因按字段顺序生成并回填。
12. 切换申请单、刷新详情或页面指纹变化后，旧会话不能继续回填。

## 13. 验收标准

- 不存在“固定主要来源缺失导致所有申请都待复核”的问题。
- 字段只要有一份有效允许证据，就不会仅因证据数量少而自动进入待处理。
- 只有真实值冲突、识别不确定或业务规则明确要求人工确认时才暂停。
- 每个字段都能看到页面原值、实际识别值、来源图片和比较结论。
- 每个证据值都能定位到对应原图。
- 审核员可以在助手内编辑人工确认值并受控回填页面。
- 每个字段都有“确认无误/标记异常”两个操作。
- 不通过字段可以整理成结构化驳回原因并回填真实页面。
- 插件不会自动点击真实页面的“通过、驳回、立即提交、取消”按钮。
- 二维码、结构化证据和主体关系页面不会出现逐字符竖排或内容混杂。
- LangGraph 仍然一次运行到底，人工操作由前端审核会话处理。
- 六类材料完整性规则、身份证/营业执照主体规则和挂靠回填安全校验保持有效。
- 过户、车源、一致性业务流程不发生行为变化。

## 14. 本计划需要用户审核的边界

实施前请重点确认以下两点：

1. “单一有效证据”是否统一允许自动通过，还是某些字段（例如报废交车日期、报废证明编号）即使只识别到一份也必须人工确认。
2. 页面“车辆所有人类型”究竟表示申请主体类型，还是新车实际所有人类型。该字段虽然不做材料字段比对，但会影响身份证/营业执照主体要求。

除以上两个业务边界外，本计划默认采用“允许来源集合 + 动态优先级 + 实际证据数量判断”的方案，不把任何一份材料的字段缺失直接视为审核异常。
