# 当前业务规则

本文件中的 `Profile`（业务配置档案）表示业务、地区和版本的组合；`MATCH`（一致）、`CONFLICT`（冲突）、`INSUFFICIENT`（证据不足）和 `REVIEW_REQUIRED`（需要人工复核）是系统统一状态。具体英文术语见[术语对照表](../参考/术语表.md)。

## 生产 Profile

- `qingdao_scrap_replacement`：青岛报废置换。
- `changchun_scrap_replacement`：长春报废置换。
- `vehicle_source`（地区 `default`）：车源审核，页面路径 `/vehicle-source`。
- 一致性当前保持未配置或人工复核入口。
- 过户能力已停用，不得重新注册为生产能力。

各个复杂业务使用独立规则文档，避免不同地区/业务的日期、材料和页面差异混在一张表里：

- [青岛报废置换审核规则](../业务/报废置换-青岛.md)
- [长春报废置换审核规则](../业务/报废置换-长春.md)
- [车源审核规则](../业务/车源审核.md)
- [新增业务规则文档模板](../业务/业务文档模板.md)

本文件负责解释跨地区的共同规则和状态语义；业务文档负责记录可以直接执行的完整配置，包括前端行为、后端字段、材料、能力、政策、任务和写回动作。以后新增地区或审核页面，原则上新增一个独立 Markdown 文件，并在本索引中登记，不要把多个地区的细节继续堆进本文件。

## 字段域

标准字段按 `application.*`、`old_vehicle.*`、`new_vehicle.*`、`scrap_certificate.*`、`invoice.*`、`vehicle.*` 和 `page_ocr.*` 组织。跨材料判断只能引用规范字段和证据来源，不能依赖 OCR 原始文本的偶然格式。

业务分区前缀（`old_vehicle` / `new_vehicle` / `vehicle`）在业务之间不重叠，因此字段键本身就带上业务归属。多个业务共用的投影表（证据策略、材料白名单、标签、上传槽位）按**合成**而不是覆盖生成：字段键和业务分区重复会在启动期报错，不允许后声明的业务悄悄吃掉前一个业务的声明。共用材料的白名单按分区隔离——同一份行驶证在报废置换只看得到 `old_vehicle` / `new_vehicle` 的白名单，在车源审核只看得到 `vehicle` 的白名单。

报废置换的组合字段协议由后端统一执行：旧车 VIN 以二维码官网字段为最高标准，页面值比较完整 VIN，行驶证和登记证只比较后 8 位；发票代码/号码与新车 VIN/OCR VIN 各自先比较两个页面原始值，再比较材料值；终端客户手机号只采用页面填写值，不参与材料比对。组合任务的页面回填必须同时写入两个字段并完成回读和失败回滚。

## 判断语义

`MATCH` 表示证据充分且一致；`CONFLICT` 表示有效证据互相矛盾；`INSUFFICIENT` 表示缺少运行判断所需证据；`REVIEW_REQUIRED` 表示系统无法安全自动判定，必须人工确认。建议生成器必须保留触发任务和理由。

## 材料与核验

材料完整性先于业务规则执行。二维码核验必须记录载荷来源、解析状态和可信度；地区政策按 Profile 选择，不得由前端推断；主体关系和车辆字段比较需要跨文档证据，缺失时进入人工复核。

### 替代材料（二选一）

有些业务允许多件材料择一提交（车源审核的“登记证书第 1、2 页”与“车辆铭牌”）。这用 `MaterialRequirement.alternative_group`（`app/businesses/material_policies.py`）声明，而不是两个独立要求：

- 组内**任一**材料满足要求时，其余成员不再报缺失，检查项理由写明“已提供同组替代材料：X”。这是“要求已满足”，不是“把缺失改成通过”——替代来源始终写在理由里。
- 组内没有任何材料满足时，成员各报一条缺失。
- 替代关系只作用于同组材料，组外材料（如必须提交的行驶证）照常报缺失。
- 不要用 `minimum_count=0` 或互相独立的两条 `minimum_count=1` 表达二选一：前者永不报警，后者会同时要求两件材料。

## 页面动作

页面写回只允许注册动作。执行前校验页面身份和唯一目标，写入后回读确认；失败时返回可见错误并尝试回滚。业务建议本身不能绕过动作白名单直接写 DOM。

## 规则执行顺序

1. 先确认页面和 Profile 有效，再确认材料是否满足能力的最低输入。
2. 对每份材料执行格式、来源、清晰度和时间有效性检查。
3. 将 OCR、二维码和人工录入统一规范化，保留原始来源和规范化过程。
4. 执行单材料规则，再执行跨材料字段比较和主体关系检查。
5. 汇总所有阻断项和待确认项，最后才计算建议。

早期阶段失败不能被后续“看起来正确”的字段覆盖。例如缺少报废证明时，即使车辆 VIN 与发票一致，也只能说明车辆字段匹配，不能给出材料完整的通过建议。

## 证据优先级

规则应优先使用可验证的结构化字段，其次使用高置信度 OCR，再使用人工确认值。不同来源产生冲突时，不得静默选择一个值；必须产生 `CONFLICT`，列出双方来源，并创建人工复核任务。证据过期、来源不明或无法定位原文时，状态为 `INSUFFICIENT`。

### 同一份材料的重复读取

一份材料可以由多张图片组成：行驶证正反面、登记证书第 1、2 页与第 3、4 页，或者用户把同一张图重复上传。这些是**同一份材料**的多次读取，不是互相独立的来源。`app/compare/aggregate.py` 的 `_deduplicate_sources`（去重来源）按（业务分区，材料类型）合并它们，审核员在材料提取值里只会看到一条“行驶证”。

材料之间的比较仍然发生在不同材料类型之间（行驶证与登记证书），那才是真正的两个来源。字段的证据策略（`sources=`、`authority=`）也按材料类型声明，不按图片。

### 同一张图的重复读取

同一张材料可能被通用 OCR 层和专用 OCR 层各读出一行。`app/compare/aggregate.py` 的 `_deduplicate_sources`（去重来源）会把同一张物理图片的多行合并为一个证据来源，合并时按以下顺序取值：

1. **优先保留与页面值一致的候选**——避免另一条低质量 OCR 把本来一致的结果误报成冲突；
2. 没有与页面值一致的候选时，取置信度最高者；置信度相同时优先带 `image_id` 且非 `ocr-` 前缀的一条。

第 1 条是**以页面值为锚的候选筛选**，只影响同一张图内部选哪一行，不改变"归一化后存在多个不同值即为 `CONFLICT`"的判定规则，也不跨越材料边界。它是全系统唯一一处此类锚定，属于规则语义，修改前必须同步本节。

## Profile 变更

新增或调整地区政策、材料要求和阈值时，先创建新的规则或 Profile 版本，绑定到测试环境验证，再切换生产引用。不要直接修改正在使用的常量，以免历史任务无法重放。停用 Profile 后，新请求不得选择它，历史响应仍必须能够读取和解释。

## 业务规则验收清单

- 正常材料能够生成预期事实和任务。
- 任一关键材料缺失会生成明确缺失任务。
- 两份材料字段冲突会生成冲突任务而不是自动通过。
- 外部核验超时会记录降级并阻断自动通过。
- 前端只展示和执行后端返回的任务，不复制规则判断。

## 字段修改规则

新增字段前先确认它是否能由现有规范字段表达；能表达时扩展字段来源或证据，不创建同义字段。字段重命名必须提供别名转换和历史读取策略。字段删除前检查 Profile、能力、Renderer 和测试引用，并保留至少一个版本的兼容读取。

### 字段的证据裁决方式

字段如何裁决证据由 `app/businesses/field_policies.py` 的 `FieldEvidencePolicy` 声明，有两种：

- **`mode="SYSTEM"`**：以页面填写值为准，材料不参与比对（手机号、主体类型）。页面为空时进入人工复核。
- **`authority=(...)`**：声明证据权威链，由 `app/compare/aggregate.py` 的 `aggregate_by_authority` 执行。**链首来源是唯一比较基准**；其余来源按各自的 `match` 窗口（`full` 全串或 `suffix8` 后 8 位）与基准比对。链首缺失或返回多个不同值时降级为人工复核——**不让位给链上的下一条来源，也不退化成多数投票**。

需要权威关系的新字段只加一条 `authority` 声明，不要再写专用的裁决函数。`old_vehicle.vin` 原先就是这样一个专用函数，已改为声明式。

链首不必是外部核验：车源审核的 `vehicle.vin`、`vehicle.brand_model`、`vehicle.engine_model` 以**行驶证图片**为唯一基准，登记证书和车辆铭牌是链上的比对目标（VIN 按后 8 位比对）。链首是 `image` 规则时用 `document_types` 限定哪几类材料算基准材料，其余材料即使存在也不参与建立基准。

工作台的**标红基准是页面原始值**，与结论基准（链首来源）不同：结论以权威为准，差异区间以页面原文为准并按比较窗口平移回完整值坐标。

差异区间落在**真正参与比对的片段**上，不落在被归一化折叠掉的字符上：`app/fields/normalize.py` 的 `comparison_view` 裁出该片段并给出偏移，`app/fields/differences.py` 生成区间时把偏移加回坐标。例如发动机型号比对只看型号本身，高亮也就不会标出中文品牌前缀。裁剪只按前后缀进行（要求被去掉的字符集中在首尾），拿不到可靠偏移时退回原串——宁可高亮位置不准，也不给出坐标错误的标记。
