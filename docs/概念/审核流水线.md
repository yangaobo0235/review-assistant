# 审核流水线、并发与任务生命周期

本文记录浏览器扩展到审核服务的现行执行链路。业务字段和政策规则仍以地区业务文档为准；本文只说明图片如何进入服务、如何调度、何时完成以及何时释放内存。

## 当前执行链路

用户点击“开始审核检查”后执行以下步骤：

1. 扩展通过 `COLLECT_PAGE_MANIFEST` 采集页面字段和图片清单。这个阶段不读取、压缩或上传图片正文。
2. 扩展调用 `POST /api/review/jobs/stream` 创建任务，请求只包含页面上下文和图片元数据。
3. 两个浏览器上传 Worker 逐张调用 `READ_REVIEW_IMAGE`。每张图片独立完成读取、压缩和 multipart 二进制上传。
4. 服务端收到一张图片后立即把它加入公平模型调度器，不等待其它图片上传完毕。
5. 所有图片上传结束后，扩展调用 `POST /api/review/jobs/{job_id}/complete` 关闭上传阶段。
6. 待该任务所有单图识别完成后，后端复用已经得到的 `AgentBatchResult` 执行材料完整性、二维码、字段比较、业务能力和最终建议，不重复调用图片模型。
7. 扩展每秒调用一次 `GET /api/review/jobs/{job_id}` 更新进度，任务进入终态后展示结果。

因此，多张图片的实际执行形态是流水线，而不是“先压缩全部图片，再上传全部图片，最后开始识别”。

## API 与兼容范围

| 接口 | 用途 |
| --- | --- |
| `POST /api/review/jobs/stream` | 创建只含图片清单的流式任务 |
| `POST /api/review/jobs/{job_id}/images` | 逐张上传图片或提交该图片的采集错误 |
| `POST /api/review/jobs/{job_id}/complete` | 声明上传阶段结束；未收到的图片按上传失败处理 |
| `GET /api/review/jobs/{job_id}` | 获取状态、阶段、进度、部分结果或最终结果 |
| `DELETE /api/review/jobs/{job_id}` | 取消任务并清理待执行工作和图片正文 |
| `POST /api/review/jobs` | 旧插件整批接口；内部转入同一流式识别队列 |
| `POST /api/review/assist` | 保留的同步调用接口，不是浏览器插件的正常入口 |

单次流式任务最多 16 张图片，单张上传正文最多 5 MB。相同 `job_id + image_id` 重复上传按幂等请求处理，不会重复识别。

## 并发参数

| 范围 | 当前值 | 目的 |
| --- | ---: | --- |
| 浏览器图片压缩 | 2 | 限制同时解码的位图数量 |
| 单个浏览器上传 | 2 | 让压缩、网络和识别重叠，同时避免占满客户端资源 |
| 全服务上传处理 | 8 | 限制服务端同时读取和编码的上传正文 |
| 单任务模型识别 | 6 | 单个大任务不能无限占用模型槽位 |
| 全服务模型识别 | 12 | 适配当前主要为三人同时使用、偶尔增加用户的场景 |
| 最终规则汇总 | 2 | 控制 LangGraph、二维码和规则汇总阶段的内存及 CPU 压力 |

后端模型队列按任务轮转。同一任务最多占用 6 个模型槽位；存在其它等待任务时，调度器优先把新空闲槽位交给其它任务。生产值由 `docker-compose.server.yml` 固定，本地可以使用同名环境变量覆盖：

```text
REVIEW_UPLOAD_GLOBAL_CONCURRENCY=8
REVIEW_MODEL_JOB_CONCURRENCY=6
REVIEW_MODEL_GLOBAL_CONCURRENCY=12
REVIEW_FINALIZE_CONCURRENCY=2
```

## 状态、阶段与进度

`status` 表示任务是否还能继续，取值为 `RUNNING`、`PARTIAL`、`COMPLETED`、`FAILED`、`CANCELLED`。

`phase` 表示当前所处阶段，取值为 `PREPARING`、`UPLOADING`、`RECOGNIZING`、`FINALIZING`、`COMPLETED`、`FAILED`、`CANCELLED`。`PARTIAL` 是最终结果状态，不是阶段；部分图片失败的任务可以表现为 `status=PARTIAL`、`phase=COMPLETED`。

进度对象包含：

- `total_count`：本次清单图片数。
- `uploaded_count`：上传阶段已经接收或完成失败归档的图片数。
- `completed_count`：模型识别成功数。
- `failed_count`：采集、上传或识别失败数。
- `timed_out_count`：识别超时数。

前端轮询等待上限为 120 秒。达到上限时，前端显示当前已有结果和提示；这个 120 秒是展示等待边界，不会把仍在运行的后端任务伪装成完成。

## 完成、取消和图片清理

“任务完成”不需要审核页面提供清理按钮。上传关闭、所有单图识别结束且最终汇总执行完毕后，后端自动进入完成阶段。

图片正文按以下规则释放：

- 不参与最终二维码核验的图片在单图识别完成后尽早释放服务端 `data_url`。
- 旧车和可能包含回收证明二维码的图片保留到最终二维码核验结束。
- 最终汇总成功、部分完成或失败后，清除该任务保留的全部图片正文。
- 调用取消接口时立即清除任务中保存的图片正文，并取消尚未开始的识别工作。
- 文字结果、状态和进度快照保留约 10 分钟，供前端轮询；这不代表图片正文仍被保留。

当前页面没有单独的“取消审核”按钮。上传或轮询发生错误时，扩展会请求取消任务；服务端也支持显式 `DELETE`，供后续 UI 或排障工具调用。

## 常见故障判断

- 页面显示 `Receiving end does not exist`：业务网页没有当前版本的 Content Script。重新加载扩展后，必须刷新业务网页，再重新打开侧边栏。
- 任务长时间处于 `UPLOADING`：检查图片读取、浏览器后台脚本和公网网络。
- 上传数增加但识别数不增加：检查模型密钥、模型服务网络和后端日志。
- 进入 `FINALIZING` 后较慢：检查二维码官网访问、规则能力超时和最终汇总并发。
- `status=PARTIAL`：查看失败数和超时数；这表示流程已经结束但部分材料未成功，不是任务仍在运行。
