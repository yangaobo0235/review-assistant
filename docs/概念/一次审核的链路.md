# 一次审核的完整链路

从审核员点「开始审核」到工作台出结果，一次请求经过的全部环节。带 ★ 的是容易踩坑、
或者设计上刻意的取舍。

```
POST /api/review/jobs/stream  (@RequestBody ReviewRequest，只带图片清单不带正文)
│
├─ ◆ 前端 · 采集        侧边栏 Content Script
│     拉页面识别清单（地址 + 页面特征）→ 识别页面业务 → 拉后端采集清单（字段别名 / 页面分区 / 材料分组）
│     ├─ 识别必须先于采集清单：清单按业务类型取，不知道业务就不知道该取哪份
│     ├─ 地址唯一 → 按地址；地址被多个业务共用 → 按页面特征筛，给不出唯一答案不猜
│     │    ★ 共用地址（一致性审核 / 过户审核都走 /consistency-*）时人工选择生效
│     ├─ 清单拉不到 → ★ 退回内置表，采集照常进行，不中断
│     ├─ 采集字段：按中文别名 + 页面区域匹配 DOM，同名多候选判歧义不猜
│     ├─ 采集图片：业务分区归组 → 过滤不可见/装饰图/空槽位 → 每桶保底 1 张，上限 16 张
│     │    ★ 类型判定先问清单声明的材料关键词（最具体的优先），问不出才退回内置表；
│     │      写死在浏览器里会让每个新业务都要改前端，改漏还静默判成别的材料
│     │    ★ 类型已知 or 命中材料关键词 or 面积够大，三者任一即入选；
│     │      面积兜底不否决前两条，小尺寸材料图（如铭牌）不会被丢掉
│     └─ 生成页面指纹（application.id + 两车 VIN/所有人，至少一个才有效）
│
├─ ◆ 前端 · 上传        两个 Worker，边读边压边传
│     每张：读取 → 压缩（最长边 2048、JPEG 0.85、并发 2）→ multipart 上传
│     同时另有 1 秒轮询任务快照，上限 120 秒
│     ★ 图片正文不走创建任务的 JSON，只走逐张上传，避免 Base64 重复搬运
│
├─ ◆ 创建流式任务  ReviewJobManager.create_stream
│     校验：单任务最多 16 张、image_id 不重复、图片必须属于创建时的清单
│     建 _StoredJob(phase=UPLOADING)
│     ★ 这一阶段不启动任何线程——流式任务完全由事件驱动
│     失败 → 422，一条记录都不留（409 是后续逐图上传阶段的错误码）
│
├─ ◆ 每张图片到达  POST /api/review/jobs/{id}/images  (multipart)
│   │
│   ├─ ◆ 网关  upload_stream_review_image
│   │     全局上传并发 Semaphore(8)；单张上限 5MB（多读 1 字节判超限）
│   │     有文件 → 二进制转 data URL 写回；无文件 → 必须带 collection_error，否则 422
│   │     任务不存在/过期 → 404；已取消或上传已关闭 → 409
│   │
│   ├─ ◆ 入队  add_stream_image
│   │     ★ 幂等：重复 image_id 直接返回当前快照，不重复识别
│   │     phase → RECOGNIZING
│   │     ★ 入队只带页面上下文，不带图片正文（否则每个排队项都深拷贝一份 Base64）
│   │     │
│   │     └─ ◆ 公平调度器  FairAsyncScheduler.submit
│   │           独立后台线程 + 独立事件循环
│   │           全局 12 / 单任务 6
│   │           ★ 按任务轮转，并防止同一个任务连续占用槽位饿死其它任务
│   │
│   └─ ◆ 单图识别  ReviewService.extract_image_async
│         分类：已知槽位按材料直接提取；未知图片先分类，置信度 < 0.70 视为不可靠
│         ★ 候选材料限制在本业务扩展包声明的集合内——政策表是跨业务合并的，
│           不限定就会让过户的「二手车发票」套用报废置换的机动车销售发票白名单，
│           字段全丢再必然重试一次；判不中宁可多走一轮分类
│         提取：按材料白名单，只输出白名单内的字段，不推测不补全
│         │
│         └─ ◆ 语义重试（最多 1 次）
│               ├─ 材料类型不符 → 换提示词重试
│               ├─ 文档级置信度 < 0.70 → 换提示词重试
│               ├─ 白名单字段全空 → 换提示词重试
│               └─ ★ 模型自报「看不清」某些字段 → 定向重读
│                     ├─ 提示词指名这些字段，要求回看原图对应区域
│                     ├─ 用 evidence_regions 裁出区域、放大后只读那一小块
│                     └─ ★ 坐标约定是推断的：区域过大或退化 → 放弃裁剪退回整图
│                          （错误的裁剪会丢掉真正要看的区域，比不裁剪更糟）
│               ★ 每次重试都写 RetrySummary（尝试次数、原因码、耗时、结果）
│
├─ ◆ 关闭上传  POST /api/review/jobs/{id}/complete
│     清单里没收到的图片标记「图片未上传」并计入失败
│     pending_count == 0 → 立即开始汇总
│
└─ ◆ 最终汇总  ReviewJobManager._finalize_async
      在独立 finalize 调度器上执行（全局 2 / 单任务 1）
      ★ 复用已识别的 AgentBatchResult，不重新调图片模型
      │
      └─ ◆ 统一主图  ReviewWorkflow.run（14 个节点，所有业务共用）
         │
         ├─ validate_input
         │     校验失败 → build_error_response → END（不执行任何能力）
         │
         ├─ extract_evidence       已复用批次，不再次识别
         ├─ assess_evidence_quality 识别阶段材料确认（页码、字段来源）
         │
         ├─ plan_capabilities      按 Profile 声明 + 实际材料决定跑哪些能力
         │     ★ 单张材料缺失不会阻止不依赖它的能力运行
         │
         ├─ execute_capabilities   阶段：INPUT_COVERAGE / EVIDENCE / PRE_COMPARE
         │     ├─ material_completeness  材料是否齐全、页码是否够
         │     └─ scrap_certificate_qr   报废证明二维码核验
         │           ├─ 解码：ZXing 为主，OpenCV 兜底；多轮重试（原图/锐化/切块）
         │           ├─ 核验：★ 官网域名白名单硬编码；http 升级为 https；保留证书校验
         │           └─ 失败不自动通过，按失败策略转人工
         │     有 BLOCKED / FAILED / NOT_CONFIGURED → record_degradation → 汇合回主链
         │
         ├─ compare_fields         ★ 审核结论从这里开始
         │     ├─ 页面值、每张材料的识别值、二维码官网值 → 统一成 FieldObservation
         │     ├─ 按字段策略过滤掉不允许的材料类型（未知材料不冒充来源）
         │     ├─ 声明了权威链的字段：链首是唯一基准，其余来源按各自窗口比对
         │     │     链首缺失 → 人工复核，不让位给下一条来源，也不退化成投票
         │     ├─ 其余字段：归一化后集合相等即 MATCH，否则 CONFLICT
         │     ├─ ★ 同一张图的多条 OCR 行合并时优先保留与页面值一致的一条
         │     └─ ★ 不确定性一票否决：模型说过看不清 → 转人工
         │           已重读过 → 理由里写明「已重读仍无法确认」
         │
         ├─ assemble_facts        阶段：POST_COMPARE / FINAL_REVIEW
         │     ├─ 地区政策：发票日期窗口、交车截止日、新车发票产地
         │     ├─ 挂靠主体关系：个人/公司的证据齐备性与主体一致性
         │     └─ verify_invoice：发票号与页面一致时提出「一键验真」页面动作
         │           ★ 只提出动作、不执行；不产出检查项，不占工作台待处理计数
         │
         ├─ prepare_review_tasks
         │     日期政策并入对应字段卡；挂靠主体关系合并辅助任务；材料问题汇总成一张卡
         │     ★ 识别诊断留在后端，不通过任务理由泄漏到工作台
         │
         ├─ derive_recommendation ★ 只要有一条 finding 就是 REVIEW_REQUIRED，否则 PASS
         │     没有打分、没有阈值、没有加权、没有投票（平均置信度只用于展示，不参与决策）
         │
         └─ build_response        把页面动作意图一并写回响应

◆ 浏览器适配器执行 page_actions
  后端只提议（action_id + payload），执行与否、如何执行由前端决定
  写回必须：身份校验 → 白名单 → 控件唯一性 → 原值校验 → 写入 → 回读 → 失败回滚
```

## 设计上刻意的取舍

| 取舍 | 原因 |
| --- | --- |
| 只提议页面动作，从不执行 | 写页面的后果由人承担，机器只给建议 |
| 冲突一律列出双方来源，不选胜者 | 静默选值在补贴审核里是责任黑洞 |
| 权威链只在业务声明时才有 | 靠票数猜不是裁决，是赌博 |
| 不确定性一票否决，宁可转人工 | 漏检的代价远高于多看一眼 |
| 重读上限 1 次，且时间不够就跳过 | 成本自限；系统繁忙时自动退回原行为 |
| 最终建议只有 PASS / REVIEW_REQUIRED | 系统不会自动「建议拒绝」，那需要业务定义 |
| 图片逐张上传，不走创建任务 JSON | 避免同一份 Base64 在协议里搬运两次 |
| 采集清单拉不到就用内置表 | 后端不可用不能让采集整体停摆 |

## 排查入口

| 现象 | 先看 |
| --- | --- |
| 图片没进审核 | 是否是空槽位/不可见/装饰图；是否超过 16 张上限；类型未知又没命中材料关键词的小图会被面积兜底丢掉 |
| 某张图没识别结果 | `RetrySummary` 里的原因码和结果；是否超时 |
| 字段全是「待复核」 | 是不是模型自报了不确定；`RetrySummary` 里有没有 `uncertain_field:` |
| 冲突但看不出谁对 | 字段有没有声明权威链；没有的话系统本就不判定谁对 |
| 整单超时 | 单任务并发上限、公平调度器的全局额度 |
| 页面动作没执行 | 前端适配器是否注册了该 `action_id` |
