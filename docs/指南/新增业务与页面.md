# 新增审核业务与页面手册

本手册说明如何接入一个新的审核业务或一个新的审核页面。核心结论：

> **一个业务的全部配置是一份声明，位于 `app/businesses/packs/<业务>.py`。**
> 新增业务 = 写这份声明 + 登记。前端零改动。

`docs/业务/` 下的地区业务文档解释**当前判断是什么**；本手册解释**如何新增**。

---

## 一、先判断属于哪一种

| 需求 | 要写什么 | 要动前端吗 |
| --- | --- | --- |
| **新业务**（如车源审核） | 一份声明 + 注册 | 不用 |
| **新页面**（已有业务的新地区/新页面） | 在声明里加一个地区或补字段别名 | 不用 |
| **新能力**（需要新的判断逻辑） | 声明里绑定 + 写一个 Handler | 不用 |
| **新页面结构完全不同**（DOM 差异大） | 声明 + 前端适配器 | 要 |

绝大多数情况是前两种，**只写声明**。

---

## 二、声明里写什么

结构定义见 `app/businesses/packs/model.py`，完整示例见
`app/businesses/packs/scrap_replacement.py`。声明由五部分组成：

### 1. 字段（`FieldDeclaration`）

每个字段声明：稳定键、中文标签、页面别名、页面区域、证据来源、比较方式、权威链。

```python
FieldDeclaration(
    key="old_vehicle.vin",              # 稳定键，只增不改
    label="报废车辆车架号",              # 面向审核员的名称
    section=OLD_SECTION,                # 后端分区
    aliases=("报废车辆车架号", "旧车车架号", "车架号"),   # 页面上的写法
    page_section=OLD_SECTION,           # 页面 DOM 区域
    section_required=True,              # 必须落在该区域，否则判歧义
    mode="PARALLEL",                    # 证据模式
    sources=("vehicle_license", "registration_certificate"),
    normalizer="vin",
    authority=(...),                    # 权威链，见下
    required=True,                      # 是否进入必审清单
)
```

**权威链**用于"某个来源说了算"的字段。链首是唯一比较基准，其余来源各按自己的
`match` 窗口与基准比对；链首缺失时转人工复核，不让位给下一条来源：

```python
authority=(
    AuthorityRule("qr_page", "二维码官网"),                    # 链首＝权威
    AuthorityRule("page", "申请页面", required=True),          # 页面缺失即人工复核
    AuthorityRule("image", "行驶证或登记证",
                  ("vehicle_license", "registration_certificate"), "suffix8"),
)
```

不需要权威关系的字段不要写 `authority`，走通用的多源比对。

### 2. 材料（`MaterialDeclaration`）

每类材料声明：材料类型、显示名、可读字段、读取指引、页面分组提示、允许出现的分区。

```python
MaterialDeclaration(
    document_type="registration_certificate",
    display_name="机动车登记证书",
    fields=("vehicle.owner", "vehicle.vin", "registration.covered_pages"),
    guidance="读取注册登记信息栏中的车辆类型、车辆识别代号……",
    hints=("登记证书", "机动车登记证"),          # 页面分组文字
    allowed_scopes=(OLD_SECTION,),               # 只出现在旧车资料区
    scoped_vehicle_fields=(),                    # 车辆字段如何跟随页面分区
)
```

`scoped_vehicle_fields` 表示"材料上的 `vehicle.X` 落到 `{当前分区}.X`"。**不在这里
声明、又没有显式路由规则的字段会被丢弃**——这是防止材料上的无关字段冒充领域字段。

### 3. 材料字段路由（`RouteDeclaration`）

材料上的字段名与领域字段名不一致时逐条声明；`{scope}` 按当前页面分区替换，一条规则
可以映射到多个领域字段：

```python
RouteDeclaration("invoice", "vehicle.owner",
                 ("new_vehicle.owner", "application.customer_name"),
                 scope=NEW_SECTION),
```

### 4. 地区（`RegionDeclaration`）

同一业务的各地区共用字段和材料，只有政策与页面地址不同：

```python
RegionDeclaration(
    Region.QINGDAO,
    replacement_policy=QINGDAO_REPLACEMENT_POLICY,   # 也可为 None
    admin_paths=("/scrap-replace-qingdao",),
),
```

地区政策能力 ID 由地区推导（`{region}_replacement_policy`），不用单独声明。
**加一个新地区 = 加一个 `RegionDeclaration`。**

### 5. 能力与页面动作

```python
capability_specs=( CapabilitySpec("material_completeness", kind="MATERIAL", ...), ... ),
binding_declarations=( CapabilityBinding("material_completeness"), ... ),
page_action_ids=("fill_affiliation_fields",),
page_interaction=True,
# 规则结论投影成页面字段的核验条目：(check_id, field)。
field_check_bindings=(("VEHICLE-MODEL-POWER", "vehicle.model"), ...),
# 审核字段就是声明的字段，页面上其他控件不进审核目录。
review_declared_fields_only=True,
material_policy=SCRAP_REPLACEMENT_MATERIAL_POLICY,
```

**每个能力都必须有对应的绑定**，否则服务启动时校验失败。

字段级回填还需要四处声明，缺一不可（详见 `docs/业务/车源审核.md` §9）：`page_action_ids` 里有一个已注册的页面写回动作、要允许写回的字段上标 `writable=True`、`writable_control_kinds` 声明已验证过的控件类型、以及 `identity_anchors` 声明页面指纹锚点。

- **没声明过控件类型的业务不限制**，这是给历史业务留的口径；新业务一律显式声明，只放开验证过的类型。
- **页面指纹锚点必须包含一个强锚点**（`*.vin` 或 `application.id`）。锚点一个都匹配不上时指纹是空串，页面写回和原图定位会在客户端被静默拒绝——报错信息不会指出是锚点写错了，只会表现为"点了没反应"。新业务接入时先确认锚点字段在该页面上存在。

两个可选声明的用途：

- `field_check_bindings`：规则结论默认作为独立任务出现在“页面外核验”里；希望审核员在字段视图里也能看到时，把结论绑到对应页面字段上。**绑定成功（字段条目真的发出来了）之后该检查不再出独立任务**——同一句话在两个地方各说一遍只会让审核员在「待处理」里把它处理两次；字段控件不在页面上时条目出不来，独立任务保留。多条检查绑到同一字段时按最坏状态合并理由，结论本身仍各自保留，每条检查自己的理由还会写进它的候选值（`CheckResultValue.check_reason`），工作台放进对应的候选框里。结论多、理由长的字段（车源的车型）尤其需要，否则审核员得在框和字段理由之间来回对照。
- `review_declared_fields_only`：默认 `False`——页面上未配置核验来源的控件会生成一条“请人工核对”条目，避免被静默忽略。新业务的审核范围就是声明字段时设为 `True`，否则工作台会被页面上大量无关控件淹没。

## 三、登记

在 `app/businesses/packs/__init__.py` 的 `BUSINESS_PACKS` 里加一行：

```python
BUSINESS_PACKS: dict[BusinessType, BusinessExtensionPack] = {
    BusinessType.SCRAP_REPLACEMENT: SCRAP_REPLACEMENT_PACK,
    BusinessType.VEHICLE_SOURCE: VEHICLE_SOURCE_PACK,      # 新增
}
```

登记之后自动生效的部分：字段清单与标签、证据策略、材料白名单与读取指引、
材料字段路由、页面地址白名单、Profile、能力绑定、以及下发给前端的采集清单。

Profile 由声明生成（见 `app/businesses/profiles.py` 的 `_build_profile`；
`build_scrap_profile` 是它的报废置换包装）。未声明扩展包的业务走
`rules_configured=False` 的降级路径，返回"规则尚未配置，请人工复核"。

分区归属由 `__init__.py` 的 `_validate_scope_ownership` 在启动期校验：
**同一业务分区不能出现在两个业务里**，否则按分区反查声明（`pack_for_scope`）
就会变成看声明顺序。字段路由只有业务分区可用，这一层保证它总能选对声明。

## 四、什么时候才需要写代码

只有三种情况：

1. **需要新的判断能力**：在 `app/businesses/rules/<业务>.py` 写一个同步 Handler
   （返回 `RuleExecutionResult`），在 `app/workflow/graph.py` 的 `builtin_rules`
   里注册，并在声明里绑定 `CapabilitySpec` + `CapabilityBinding`。三处缺一不可：
   **没有注册表条目，`BusinessRuleRegistry.validate` 会在启动期抛 `UnknownBusinessRule`**。
   超时、重试和失败策略由 `CapabilitySpec` 声明，不需要写在 Handler 里。
2. **页面 DOM 结构完全不同**：现有采集器按中文别名 + 页面区域匹配，多数页面
   只需要在声明里补别名。结构差异大时才需要前端适配器。
3. **需要新的展示形态**：在 `review-extension/src/components/workbenchRenderers.tsx`
   注册新的 Renderer。通用任务用默认渲染器即可。

如果新业务要改动引擎侧的投影表（`field_policies`、`fields`、`materials`、
`completeness` 的中文标签、`service` 的槽位表），先确认它们是否已经按
`BUSINESS_PACKS` 合成——合成之后新增业务不需要再碰这些文件。

**主图（`app/workflow/graph.py`）不按业务复制。** 只有生命周期本身变化时才改主图。

## 五、交付清单

- [ ] 声明：字段、材料、路由、地区、能力绑定、页面动作
- [ ] 登记到 `BUSINESS_PACKS`
- [ ] 测试：字段标签与必审顺序、证据策略覆盖、每类材料有名称/白名单/指引/分组提示、
      每个能力有绑定、每个地区有政策和页面地址
- [ ] 测试数据：最小成功样本、关键字段缺失、字段冲突、低质量材料、外部服务超时、重复请求
- [ ] 业务文档：`docs/业务/<业务>.md`（从 `docs/业务/业务文档模板.md` 起），并在
      `docs/索引.md` 和 `docs/概念/字段与判定规则.md` 登记；无法确认的页面结构写进
      文档的“待确认点”，不要猜一个默认通过的规则
- [ ] 前端：新图片类型要同时补 `src/browser/content.ts` 的 `classifyImage` 和
      `src/browser/business-scope.ts` 的 `physicalDocumentTypes`，否则图片类型只能靠
      模型识别；新业务的分组标题和别名由清单下发，不用改前端
- [ ] 回滚方式

## 六、禁止事项

- 复制一份按城市命名的主图
- 在 Profile 或声明之外再写一份字段清单、材料白名单或别名表
- 在 React 组件里计算后端资格规则
- 在后端写 DOM 选择器或依赖浏览器全局变量
- 通过 `Any`、未注册字符串或隐式字段绕过契约
- 恢复 `review-extension/public/*.js` 旧双源码或已停用过户 Profile

## 七、前端采集清单

后端通过 `GET /api/review/collect-manifest?business_type=...` 下发字段别名、
页面分组标题、材料分组关键词、上传槽位，以及**展示用的中文名**
（`fields[].label` / `materials[].label`）。前端在采集前拉取并应用；
**拉取失败时退回内置表，采集不中断**。

侧边栏和 Content Script 是两个独立的 JS 运行时，各自应用同一份清单：采集判定
（别名匹配、分区、图片筛选）发生在 Content Script，展示用的中文名（字段名、
材料名）发生在侧边栏。所以新增业务时**后端声明一次就够了**，前端不需要再各改
一份中文名表。

尚未声明扩展包的业务返回 404，前端同样退回内置表。

清单与前端内置表的一致性由 `review-extension/tests/collect-manifest.test.mjs`
锁定：它用后端生成的 fixture 走前端的真实查找路径，逐条比对结果。
