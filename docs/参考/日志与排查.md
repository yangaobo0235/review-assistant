# 日志与排查

日志的目标是让开发人员只看后端控制台，就能回答一次审核发生了什么。日志用于诊断，**不能替代 `ReviewResponse` 中的业务证据**。

> **现状说明（先读）**
>
> 目前**没有统一的事件协议**。服务用 Uvicorn 的控制台输出直接打日志，结构化程度不一致：
> 主图的事件和每项能力的执行结果用 `key=value` 格式（`review workflow started` /
> `review node completed` / `review capability completed`），其余是多处零散的提示行（中英文混排）。
>
> 单张图片的识别结果记录在 `Agent image completed` 一行里；更细的逐次尝试原因
> （如 `uncertain_field:xxx`）仍在响应的 `retry_summary` 里，控制台不重复。
> 新增日志时按下面的约定补，不要另起一套前缀。

## 日志格式

### 结构化事件

主图和能力执行使用 `review <事件名> key=value` 格式，字段稳定、便于 grep：

```text
INFO review workflow started trace_id=abc123 profile=scrap_replacement/qingdao/1.0
INFO review node completed node=compare_fields duration_ms=42.3 trace_id=abc123
INFO review capability completed capability=affiliation_subject status=SUCCEEDED attempts=1 checks=2 trace_id=abc123
```

- `trace_id`（链路 ID）是一次审核的主索引，异步审核另外带 `job_id`（任务 ID）
- 排查时先复制这两个 ID 再按时间顺序查看
- `review capability completed` 每项能力一条，无论成功、跳过还是失败都会留下；
  `status` 是能力的终态（`SUCCEEDED` / `SKIPPED` / `FAILED` / `BLOCKED` / `NOT_CONFIGURED`），
  一条 `capability=` 都没有就是计划阶段就没排上它

### 其余日志

任务与调用侧使用普通消息行：

```text
INFO  Review request received: trace_id=abc123 application_id=APP-1 field_count=16 image_count=8
INFO  Stream review job created: job_id=job-42 expected_images=8
INFO  Agent image completed: image=old_vehicle-03 type=scrap_certificate accepted_field_count=6 uncertain_field_count=1 uncertain_fields=new_vehicle.origin retry_attempts=1 retry_result=succeeded
WARNING Agent image timed out: image=old_vehicle-05
WARNING Agent image failed: image=new_vehicle-01 error_type=RuntimeError error_code=CAPABILITY_FAILED error_detail=...
WARNING Capability qingdao_replacement_policy failed: TimeoutError
INFO  Review job finished: job_id=job-42 status=COMPLETED completed=8 failed=0 timed_out=0
INFO  Review completed: trace_id=abc123 recommendation=REVIEW_REQUIRED comparison_count=18 issue_count=1
INFO  局部重读放弃裁剪 image=1600x1200 boxes=[[400, 300, 900, 600]]
```

> **读 `retry_attempts` / `retry_result`**：重读条件的上限由 `RetryPolicy.semantic_retry_count`
> 决定（默认 1，即最多重读一次）。三个取值对应三种情况，`uncertain_fields=` 里的字段
> 因此要分开解读：
>
> | 取值 | 含义 | 该往哪查 |
> | --- | --- | --- |
> | `retry_attempts=0 retry_result=-` | 没触发重读条件 | 这些字段是第一次识别就不确定的 |
> | `retry_attempts=1 retry_result=succeeded` | 重读跑过，结果以重读为准 | 重读也没解决，看提示词或图片质量 |
> | `retry_attempts=0 retry_result=skipped` | 满足重读条件但整单剩余时间不足 2 秒 | 是时间不够，不是字段难识别 |
>
> 重读本身失败或超时时走告警分支，不会有 `Agent image completed` 这一行，
> 改看 `Agent image failed` / `Agent image timed out`。

新增日志的约定：

- 结构化字段一律 `key=value`，键名用小写英文
- **不记录**身份证号、完整发票号、OCR 原文、图片数据、密钥或完整第三方响应
- 只记录标识、状态、数量、类型和耗时

## 日志点清单

| 位置 | 级别 | 说明 |
| --- | --- | --- |
| `app/main.py` | INFO | `Review request received` / `Review job requested` / `Stream review job created` / `Review completed` |
| `app/services/jobs.py` | INFO | `Review job finished`，带完成、失败、超时数量 |
| `app/workflow/graph.py` 图入口 | INFO | `review workflow started`，带 trace_id 和 Profile |
| `app/workflow/graph.py` `_instrument` | INFO | `review node completed`，每个节点一条，带耗时 |
| `app/workflow/service.py` | INFO / WARNING | `Agent image completed`（材料类型、接受字段数、不确定字段数与字段名、重读次数与结果）；超时或失败的告警 |
| `app/capabilities/registry.py` | INFO / WARNING | `review capability completed`，每项能力一条，带状态和检查项数；处理器抛异常时另有一条 `Capability ... failed`，带异常类型 |
| `app/workflow/image_focus.py` | INFO / WARNING | 局部重读放弃裁剪时记录原始坐标；图片处理依赖缺失时告警 |

## 排查路径

1. **请求根本没进后端**：控制台没有 `Review request received`，先查扩展端的地址和网络。
2. **任务创建失败**：`Stream review job created` 没出现，看 HTTP 状态码（422 是请求本身不合法）。
3. **任务卡住**：有 `Stream review job created` 但没有 `review workflow started`，说明图片还在上传或识别阶段——看任务快照的 `phase` 字段。
4. **主图走到哪一步**：按 `trace_id` grep `review node completed`，缺哪个节点就是卡在哪个节点。
5. **单张图有没有识别出来**：grep `Agent image completed` 看材料类型、接受字段数和 `uncertain_fields`；没有这条就是超时或失败，grep 对应告警，再去响应的 `retry_summary.attempts` 看详细原因码（例如 `uncertain_field:xxx` 表示定向重读后仍不确定）。
6. **不确定字段是本来就不确定还是重读后仍不确定**：看同一行的 `retry_attempts` / `retry_result`（含义见上表）。`succeeded` 说明重读跑过但没解决——问题在提示词或图片质量；`skipped` 说明是整单时间不够，不是字段难识别。
7. **为什么是人工复核**：grep `uncertain_fields=` 看模型自报的不确定字段——它直接触发一票否决；再看 `review capability completed` 里有没有 `status=FAILED` / `BLOCKED`，据此对照响应的 `capability_results` 和 `issues`。
7. **能力到底跑了没有**：按 `trace_id` grep `review capability completed`，缺哪项能力就是计划阶段没排上它（对照响应的 `capability_plan`）。
8. **结论是人工复核但看不出原因**：回到 `ReviewResponse`——`agent_advice.findings` 逐条列出每个 finding 的 `check_id`、状态和理由。

## 已知缺口

**逐次重试的原因码**（`retry_summary.attempts`）只在响应里，控制台只汇总到单图一行。
需要逐次原因的场合不多，暂不补；新增日志时仍按上面的约定，不要另起一套前缀。
