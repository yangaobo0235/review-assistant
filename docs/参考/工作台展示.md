# 审核工作台前端展示规范

`Workbench`（审核工作台）是展示任务和证据的界面；`Renderer`（渲染器）把 `ReviewTask`（审核任务）转换为组件；`PageAction`（页面动作）是经过授权的页面写回操作。本文只规定如何展示和操作，不重新计算后端规则。

本文档规定后端审核结果如何在浏览器扩展中展示、筛选、定位和执行页面动作。它是前端的展示契约，不是第二套审核规则。前端可以决定布局、标签、颜色、折叠状态和交互方式，但不得改变后端的状态、理由、证据或建议。

## 1. 展示目标

审核员打开工作台后，应能在很短时间内回答五个问题：

1. 当前审核是否可以继续，以及页面是否仍然是提交审核时的页面。
2. 哪些字段已经一致，哪些字段冲突，哪些字段证据不足。
3. 每个结论来自哪张材料、哪一页、哪个字段或哪个外部核验。
4. 当前还需要审核员处理什么，处理后会影响什么。
5. 哪些动作可以安全回填，回填是否成功并已回读确认。

任何只显示“通过/失败”而隐藏来源、理由、缺失和降级信息的页面都不符合本规范。

## 2. 页面整体结构

字段优先 Profile 使用统一工作台，推荐顺序如下：

1. **顶部摘要**：显示自动通过数量、已人工处理数量、待处理数量和当前页面状态。
2. **视图标签**：待处理、全部字段、页面外核验；数量必须与实际任务数量一致。
3. **任务索引**：按后端 `sequence` 或稳定任务 ID 排序，显示字段名称和状态。
4. **任务详情**：显示页面原始值、材料提取值、证据来源、理由、差异、高亮和动作。
5. **底部消息区**：显示回填、回读、回滚、重新采集和错误信息。

通用 Profile 没有专用渲染器时使用 `ReviewTaskWorkbench`；长春和青岛使用同一个 `ScrapReplacementReview` 渲染器，通过 Profile Key 注册，不在组件内部复制两套页面。

## 3. 状态和视觉语义

| 后端状态 | 中文显示 | 视觉语义 | 是否允许自动通过 |
| --- | --- | --- | --- |
| `MATCH` | 一致/满足/通过 | 绿色文字或边框、成功图标 | 仅在所有阻断条件满足时允许 |
| `CONFLICT` | 冲突/不一致/不满足 | 红色文字、红色边框或左侧标记 | 不允许 |
| `INSUFFICIENT` | 待复核/无法校验/证据不足 | 橙色文字、警告标记 | 不允许 |
| `REVIEW_REQUIRED` | 待复核 | 橙色或中性色警告 | 不允许 |
| `MISSING` | 缺少材料 | 红色或橙色缺失标记 | 不允许 |
| `UNCERTAIN` | 识别不确定 | 橙色不确定标记 | 不允许 |

颜色不能是唯一信息。每个状态必须同时显示文字、图标或可访问标签；冲突不能只用浅红背景表示。建议区域还要显示“审核建议：通过”或“审核建议：需要人工复核”。

`MATCH` 只表示该项证据一致，不表示整单已经通过。顶部的整体建议必须由后端 `recommendation` 决定，前端不得通过统计绿色行自行计算。

## 4. 字段比较展示

字段任务至少展示：字段标题、页面原始值、材料提取值、来源名称、任务状态和后端理由。

- 页面值缺失显示“未采集”，不能显示为空白让审核员误以为没有该字段。
- 材料值缺失显示“未识别”或“没有可靠证据”，并解释是缺图片、读取失败、识别失败还是字段未提取。
- 两边值相同显示“字段一致”，保留可展开的证据来源。
- 两边值不同显示“字段冲突”，页面值和材料值同时保留，不能覆盖其中一个。
- 日期、车架号、车牌号等字段可以使用后端提供的规范化比较和差异范围；前端只能渲染差异，不能自己归一化后改变结论。

字段列表中的状态颜色、详情卡片中的状态和异常筛选必须来自同一个 `result_status`。禁止列表显示“通过”而详情显示“待复核”。

## 5. 不一致和证据高亮

证据高亮由 `EvidenceFact.conflicting`、`differences` 和后端任务状态驱动：

- 有明确多数基准值时，只标出与基准不一致的证据片段，并标注“与基准值不一致”。
- 只有两条互相冲突的证据时，两边都要显示对方值，不能擅自选择一边作为正确值。
- 三条及以上全部冲突且没有多数值时，整条证据标记为冲突，提示“未形成多数值”。
- 没有差异位置时只显示值级别的冲突，不伪造字符级高亮。

高亮必须保留原文和来源。不能把高亮后的文本提交给后端，也不能把视觉上的多数值变成自动采用值。

## 6. 证据来源和原图定位

证据来源应使用稳定的中文标签：申请页面、机动车销售发票、机动车登记证书、行驶证、报废机动车回收证明、营业执照、身份证、二维码官网或图片证据。来源标签来自 `EvidenceFact` 的来源和文档类型映射，不根据图片文件名猜测。

每条图片证据在有 `image_id` 时提供“查看原图”。点击后应：

1. 在当前审核页面或受控预览中定位对应图片；
2. 尽可能滚动到原图并添加短暂高亮；
3. 显示材料类型、业务范围、分组顺序和来源；
4. 如果图片已经失效，显示“原图不可用”，保留后端证据文字，不伪造定位成功。

原图定位只改变浏览器视图，不改变审核状态。图片二进制不能写入日志或公开错误消息。

## 7. 材料完整性展示

后端可以继续返回 `MATERIAL-GROUP`（材料完整性任务）和 `material_completeness` 报告。当前青岛、长春报废置换工作台不展示该任务，也不把它计入页签数量；该前端策略不修改后端材料规则、响应数据或最终建议。其他启用材料 Renderer 的工作台如果展示该任务，只能回答材料是否齐全，不得展示字段识别异常、OCR 限制或单字段识别详情。

材料任务必须显示清单，而不是只显示一条“材料不足”：

- `PRESENT`：显示材料名称和已提供状态。
- `MISSING`：显示材料缺失状态。
- `UNCERTAIN`：显示材料待确认状态。
- 图片读取失败、识别失败和字段未提取属于后端诊断，不在材料任务中展开。

登记证第 1、2 页必须分别展示已确认页和缺失页；不能因为上传了一张登记证图片就显示“材料完整”。

## 8. 二维码和外部核验展示

二维码任务显示解析状态、二维码来源、官网字段、域名校验、访问状态和失败原因。外部服务超时、不可访问或不确定必须显示降级提示，并进入人工复核。前端不得把“网页打开成功”显示成“业务核验通过”，只有后端 `CheckResult` 为 `MATCH` 才能显示满足。

## 9. 主体关系展示

后端继续计算并返回主体关系任务。当前青岛、长春报废置换工作台按稳定任务 ID 排除主体关系及其辅助任务，同时不采集、不展示“报废车挂靠”“新车挂靠”两个页面字段。该展示策略不得通过中文标题匹配实现。

后端在主体关系 `MATCH` 且返回两个完整 `page_fill_intent`（页面填写意图）时，会通过 `autoFillAffiliation`（挂靠自动填写）把规则推导的主体类型写入两个挂靠下拉框。**当前工作台只是隐藏了挂靠任务及其辅助任务，写入路径仍然启用**，它只是不在界面上单独展示；不要把它当成已停用能力而从会话编排中移除。

写入器保留页面身份校验、唯一性检查、原值校验、回读和回滚保护。写入失败会把整个会话置为 `STALE_PAGE`（页面已失效）并禁用全部回填按钮，因此改变这段行为前必须先确认页面控件仍然存在。

## 10. 回填和页面定位

普通字段回填流程：

1. 审核员在任务中选择某条材料值，或手工输入候选值。只要任务绑定了 `page_target_field`（页面定位字段），即使任务在侧边栏以 `ASSISTANT`（助手任务）展示，也必须提供人工输入框；输入框初始值为页面原值，允许审核员修正页面值和材料值都不可信的情况。
2. “回填此值”按钮只在存在可写候选、任务状态不是 `MATCH` 且 `writable`（允许写回）为真时出现。按钮和人工输入框都调用同一个受控写回链路，不能各自实现一套 DOM 操作。

3. 前端显示即将写入的字段和目标控件。
4. 写入前重新检查页面实例、采集批次、控件唯一性和原值。
5. 写入后回读页面字段，成功时显示“已回填并回读，已定位到页面字段”。
6. 页面目标应滚动到可视区域、获得焦点并短暂高亮约 4 秒，帮助审核员确认实际写入位置。
7. 回读不一致时显示失败原因并回滚；不能显示成功。

发票代码/号码任务和新车车架号任务是组合字段任务。后端必须先比较页面两个原始值，再比较材料值；前端显示两个页面原始值。点击“回填此值”时，两个页面字段必须在同一授权动作中完成唯一控件校验、原值校验、写入、回读和失败回滚，不能只写入其中一个字段。

开票金额回填使用字段级金额回读：`423000.00`、`￥423,000.00` 等等价格式在页面写回确认阶段视为同值；只有货币符号没有数字时按空金额采集。该规范化只用于 DOM 写回确认，不改变后端字段比较结论。回读失败仍必须回滚。

## 11. 页面失效和操作禁用

检测到页面刷新、标签页切换、业务身份变化、采集批次过期、目标控件变化或页面指纹不匹配时，工作台显示“页面操作已停止”，禁用所有回填按钮，并提供“重新采集并复核”。旧任务可以继续阅读，但不能继续写页面。

网络错误、协议错误和服务端失败要区分显示。网络错误提示可以重试；协议错误提示版本不兼容；业务失败提示人工复核。不能把三类错误统一显示为“审核不通过”。

## 12. 人工处理状态

前端可以记录审核员对任务的“已处理”或“标记人工复核”操作，但不能篡改后端原始 `MATCH`、`CONFLICT` 或 `INSUFFICIENT`。人工处理状态只用于工作台进度显示；最终建议仍以服务端结果和产品规定的人工确认流程为准。

## 13. 可访问性和一致性

状态不能只依赖颜色；按钮需要明确文字和禁用原因；原图按钮需要可访问名称；高亮文本不能依赖颜色区分。所有 Profile 使用同一套状态标签、证据标签、回填成功/失败文案和页面失效文案，地区差异只出现在业务名称、政策理由和材料要求中。

## 14. 变更要求

新增任务类型时，先确认通用 Renderer 能否展示；不能展示时新增 Renderer Registry 条目，并记录输入字段、状态映射、证据展示、操作权限和空状态。不得在 `ReviewResults.tsx` 或地区组件中增加业务判断来修补后端结果。修改颜色、状态文案、筛选逻辑、证据高亮、原图定位或回填反馈时，必须补充对应前端测试和截图/交互验收说明。
